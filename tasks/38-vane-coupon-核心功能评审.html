01

核心数据流与职责边界

券领域把「可变行为」全部压进内核 state，Core 只读 props 渲染面额区与标题。这个分层的代价是： 任何规则判定都必须由插件写进 state，再由消费方或 ClaimState 读 state 才生效； 只要某条规则没有写 state，展示与门控就会分叉——本轮 5 条 P1 全部产生于这条链路。

① 券面数据

宿主传入 coupon（amount / threshold / validTo / total / claimed / quota / stackable）。

② 内核 state

phase、validity、countdown、quotaReached、claimedAt，写入即触发 context 重建。

③ 事件钩子

onMount / onPropsChange / onPhaseChange / onValidityChange 计算并写 state。

④ 分段插槽

before（角标）→ 本体 → after（有效期 / 规则）→ footer（领取按钮）→ overlay。

⑤ Core 拼装

面额 + 门槛、标题、挂载标记；不参与任何可用性判定。

02

已验证成立的核心机制

这些是阅读时最容易被误判成 bug 的部分，逐条对照代码与单测后确认成立，不应作为问题上报。

✓相位流转与终态保护是成立的

TERMINAL_PHASES 把 used / soldout / expired 固定为终态，gatePhase 对终态直接返回 null，不会被后续有效期判定打回。transition 值相同不写，避免自激重渲染。

✓领取失败/异常回退正确

失败与 catch 都回退 available 并调用 onClaimError；claim 未配置时视为成功，符合纯展示场景的文档承诺。

✓绝对有效期边界解析正确

notStarted = ts < validFrom、expired = ts > validTo，端点当刻仍算有效；remainingMs 用 Math.max(0, …) 不会出负数，区间文案由 fmtDate 稳定格式化。

✓相对有效期的 claimedAt 锚定生效

领取成功时 phase 与 claimedAt 同批 setState，随后 onPhaseChange 在 effect 内执行，evaluate 读到的已是新 state，文案从「领取后 N 天」切换为「YYYY.MM.DD 领取，N 天内有效」。

✓写 state 前做结构化比较

sameValidity 用 JSON.stringify 比较，ClaimState 用 context.state?.phase === next 早退；重复评估不会造成 state 抖动。

✓规则折叠与空数据安全

rules ?? [] 空数组直接 return null；按条数 slice 而非 line-clamp；按钮带 aria-expanded，展开态写 rulesExpanded 供宿主复位。

✓插件渲染异常被隔离

内核 renderPluginSlot 对每个插件单独 try/catch 再包 PluginErrorBoundary，一个坏插件只丢自己那一段；单测「一个插件渲染抛错不影响其他插件的插槽输出」通过。

✓门槛文案回退正确

thresholdText 优先覆盖；threshold > 0 生成「满 X 可用」，0 / undefined 归为「无门槛」；cash / discount 两种面额的货币符号与单位分支正确。

03

P1 问题（真实接入必然踩到）

这 5 条的共同点：组件显示的状态与它实际允许的行为不一致。前三条都是「券已经不可领，按钮仍是「立即领取」」， 第四条是运行时换插件配置后初始化不再执行，第五条是可用性判定整体缺位。

P1-1 · 「已抢完」只画进度条，领取按钮照常可领（soldout 不读 total/claimed）

P1
证据 1
packages/vane-coupon/src/custom-plugins/ProgressPlugin/create.tsx:38-50——进度条已经算到「已抢完」
const total = config.total ?? c.total;
const claimed = config.claimed ?? c.claimed;
const remaining = Math.max(0, total - claimed);
let text = `已抢 ${pct}%`;
if (remaining === 0) {
  text = "已抢完";          // 展示层：券已没了
}
证据 2
packages/vane-coupon/src/custom-plugins/ClaimStatePlugin/create.tsx:68-77——门控只看插件创建的 config.stock，完全不读 coupon.total / claimed（CouponData 也没有 stock 字段）
const gatePhase = (context) => {
  const current = context.phase;
  if (TERMINAL_PHASES.has(current)) return null;
  const validity = context.state?.validity ?? null;
  if (validity?.expired) return "expired";
  if (typeof config.stock === "number" && config.stock <= 0) return "soldout";
  return null;
};
后果
限量券把 total=1000 / claimed=1000 下发时，卡片上写着「已抢完」，按钮仍是可点击的「立即领取」；点击才走 gatePhase，而它返回 null，直接发起领取请求。服务端拒绝后 UI 回退 available，用户会反复点。素材库 demo（07-progress / scenarios/02-limited-rush）正好是这个配置。
建议
把「已抢完」收敛成单一事实：Progress 或 ClaimState 在 total > 0 && claimed >= total 时写 state.phase = "soldout"，并让 gatePhase 读它；或者直接让 gatePhase 读 context.coupon.total/claimed，不要依赖 config.stock。补测试：claimed=total 时按钮 disabled。

P1-2 · 每人限领超限不门控：quotaReached 写了 state，但没有任何消费者

P1
证据 1
packages/vane-coupon/src/custom-plugins/QuotaPlugin/create.tsx:36,43,49——注释与 description 都承诺「供领取按钮门控」
description: "…超限写 state.quotaReached 供领取按钮门控",
onMount:      (context) => { if (reached) context.setState({ quotaReached: true }); },
onPropsChange:(context) => { context.setState({ quotaReached: reached }); }
证据 2
packages/vane-coupon/src/custom-plugins/ClaimStatePlugin/create.tsx:68-77, 129-136——gatePhase 与点击前二次守卫都只查 validity.expired 与 config.stock；全包检索 quotaReached 仅出现在 QuotaPlugin 自身（grep 结果 5 处，均无读取）。
后果
用户已领满（purchasedCount >= quota）时，卡片显示「已达限领上限」的红色提示条，下面的领取按钮仍是「立即领取」且可点击；点击后进入 claiming → claimed（本地乐观成功），实际服务端按限领拒绝，本地已把券标成「已领取/展示券码」（CopyCode 只在 claimed/used 显示）。这是规则判定与展示直接矛盾，也影响埋点（Analytics 会记录一次成功相位变化）。
建议
ClaimState 在 gatePhase 内读 context.state.quotaReached（或读 coupon.quota 与已领数），命中时返回一个不可领态（建议新增 quota-limited，或直接用 soldout/used 的文案覆盖机制）；同时让点击守卫复用同一函数。补测试：purchased=quota 时按钮 disabled 且不触发 claim。

P1-3 · 过期不随时间收敛：页面停留跨过 validTo 后仍可领取

P1
证据 1
packages/vane-coupon/src/custom-plugins/ValidityPlugin/create.tsx:108-113, 123-132——evaluate 只在三个事件钩子里调用，没有定时器
hooks: {
  onMount:        (context) => { evaluate(context); },
  onPropsChange:  (context) => { evaluate(context); },
  onPhaseChange:  (context) => { evaluate(context); },
}
证据 2
同文件 :49-67 的 expired = ts > coupon.validTo 依赖调用时刻的 now()；state 里的 validity 一旦写入就不再刷新。唯一带定时器的是 CountdownPlugin，且它只服务于 startAt（开抢），不覆盖 validTo。
后果
券详情页/悬浮卡片长时间停留（大促页面很常见）跨过截止时间后：有效期文案仍显示「2026.11.01 前」，按钮仍是「立即领取」；点击时 gatePhase 读的是陈旧的 state.validity.expired=false，所以连点击守卫也失效，直接发请求。埋点同样按成功路径记录。
建议
ValidityPlugin 在 absolute 模式下按剩余时间挂一个 setTimeout（或复用 Countdown 的 tick 链）到点重算并写 state；同时 gatePhase 在点击时用 now() 重算一次，而不是只信 state。补测试：注入 now 跨过 validTo 后按钮进入 expired。

P1-4 · 运行时重建同名插件后，新实例的 onMount 永远不执行

P1
证据 1
packages/vane-coupon/src/components/CouponPlugin/withPlugins.tsx:80-83——HOC 只在挂载时跑一次钩子链
useEffect(() => {
  void execute("onMount");
  // eslint-disable-next-line react-hooks/exhaustive-deps
}, [execute]);
证据 2
packages/plugin-core/src/react/usePluginRuntime.ts:100-117 + packages/plugin-core/src/manager/PluginManager.ts:111-129——插件引用变化时 manager.clear()（先执行旧实例的 cleanup）再 registerAll，但钩子链不会再跑
useLayoutEffect(() => {
  manager.clear();              // 倒计时 clearTimeout、键盘监听移除…
  manager.registerAll(stablePlugins);
}, [stablePlugins]);
后果
宿主在运行时换配置（例如轮询把 stock 从 10 改成 0、把 startAt 改成新的开抢时间、换一份 claim 回调）时，会创建新的插件对象触发起重注册：旧 Countdown 的 setTimeout 被 cleanup 清掉，新实例的 onMount 不会再启动倒计时；Validity 与 ClaimState 也不再初始化 state（卡片停留在旧的 phase/validity）。文档承诺的「按 key 重建插件」在这条路径上只完成了一半。
建议
在 stablePlugins 变化的 layout effect 里，对本次新注册的实例执行一次 onMount（可按插件引用 diff 只跑新增/替换项）；或给内核加 onRegister 钩子。补测试：同名插件换配置后倒计时 timer 重新挂载。

P1-5 · 可用性判定整体缺位：门槛 / 商品范围 / 互斥 / 叠加只有字段与文案

P1
证据
packages/vane-coupon/src/components/CouponPlugin/plugins/types.ts:25-62 声明了 threshold / stackable / quota / channels，但全包检索这些字段只出现在渲染钩子：stackable 仅 StackPlugin:44-60，channels 仅 ChannelPlugin:28-29，threshold 仅 CouponCore.tsx:63-67 生成一句文案。不存在 isUsable / applicable / matchOrder 之类判定函数，也没有「券适用范围（category / sku 白名单）」与「互斥组」字段。
// CouponCore.tsx:63-67 —— threshold 的唯一用途是文案
const thresholdText =
  coupon.thresholdText ??
  (coupon.threshold && coupon.threshold > 0
    ? `满${coupon.threshold}可用`
    : "无门槛");
后果
券列表/结算页接入时会自然地把「组件显示的券」当成「当前订单可用的券」：组件会照常展示「满 199 可用」的券，即使购物车只有 99 元；「可叠加」角标来自上游字段，组件不做叠加冲突校验；包内也没有商品范围字段可表达。金额与门槛没有任何判定出口，消费方必然在组件之外重写一套规则，且两套规则会漂移——这正是「券的可用性判定与展示不一致」的根源。
建议
补一个纯函数模块（如 coupon/eligibility.ts）：isEligible(coupon, order) 判定门槛 / 有效期 / 商品范围 / 互斥组，并把结果写进 state.eligible 供 ClaimState 与宿主复用；数据模型补 scope（sku/category）、exclusiveGroup、stackingRule。至少要在 README/类型注释中明确「本包不做可用性判定」，避免假契约。
04

P2 问题（可排期，不影响主链路）

契约、成本与可维护性问题；单独看不致命，组合起来会拉高接入与排障成本。

P2-1 · 领取按钮没有重入锁，异步成功后也不校验挂载

P2
证据
packages/vane-coupon/src/custom-plugins/ClaimStatePlugin/create.tsx:129-152：handleClick 用渲染时闭包的 phase 判断，transition(…, "claiming") 之后没有读取最新 context.state.phase 的二次守卫；await 之后直接 setState({ phase: "claimed" })。
后果
双击/键盘连按（原生按钮在重渲染前仍可点）会发起两次领取；卸载后 await 返回仍会写 state（React 18 不报错，但会浪费一次更新并可能触发已卸载组件的回调）。
建议
用 context.state.phase !== "available" 作为点击守卫，或用 ref 锁 + finally 释放；异步后用 isMountedRef 判断。订单类组件建议把「请求 id」对齐，防止后发先至覆盖。

P2-2 · RemindPlugin 依赖 idle 相位，但默认相位是 available，插件默认永不渲染

P2
证据
withPlugins.tsx:49 phase: (state.phase ?? "available")；RemindPlugin/create.tsx:35 if (context.phase !== "idle") return null。ClaimState 未配 initialPhase 时不会写 phase，于是 Remind 永远走不到 idle。
后果
接入方按 demo 只装 createRemindPlugin() 时会觉得「插件没生效」；必须额外创建 ClaimState 并传 initialPhase: "idle" 才能出现，文档没写这个隐含依赖。
建议
Remind 改为按 countdown > 0 或 validity.notStarted 渲染；或在 Remind 的 doc.json 明确「需 initialPhase: idle」。

P2-3 · 面额 / 门槛不做格式化与合法性校验，0 与 NaN 都被吞成「无门槛」

P2
证据
CouponCore.tsx:95-105 直接渲染 {coupon.amount}；:63-67 用 coupon.threshold && coupon.threshold > 0 判定。
后果
接口下发字符串金额（"10.00"）能显示但类型不成立；10.5 显示为「¥10.5」而非两位小数；NaN（如折扣券 amount 计算失败）既不报错也不进入兜底，直接渲染出「NaN」；threshold: NaN / 负数 会被静默归类为「无门槛」，属于会误导用户的展示降级。
建议
加一个 formatAmount（cash 固定两位、discount 去掉多余 0），并对非有限值走兜底文案；门槛判定改用 Number.isFinite 且区分「非法数据」与「无门槛」。

P2-4 · context 每次渲染重建，四个插槽每次渲染全量求值

P2
证据
withPlugins.tsx:43-59 的 extendContext 依赖 [props]，而 props 由父组件传入、通常是新对象；plugin-core/src/react/usePluginRuntime.ts:138-157 的 useMemo 依赖 extendContext，因此 context 每次渲染都是新引用。
const extendContext = useCallback((base: any): any => { … }, [props]);
const context = useMemo(() => extendContext ? extendContext(ctx) : ctx,
                       [props, data, state, deviceInfo, bus, extendContext]);
后果
任何父组件重渲染（哪怕 coupon 数据完全没变）都会让 renderPluginSlot 在 :128-143 重新调用 14 个插件的渲染钩子，并对每段做排序和 ErrorBoundary 重建；在券列表里 N 张卡 × M 个插件时是平方级成本。
建议
把 extendContext 的依赖改为 [props.coupon, props.data] 这类稳定原语，并对 slots 做 useMemo（依赖 orderedPlugins + ctx）；或让内核暴露 stableContext。

P2-5 · onPropsChange 在每次父渲染都触发，Quota 无条件写 state 造成额外一帧

P2
证据
withPlugins.tsx:88-95 以 props 引用比较；QuotaPlugin/create.tsx:47-51 在 onPropsChange 里无条件 setState({ quotaReached: reached })（即使值没变）。
const prev = prevPropsRef.current;
if (prev !== props) { prevPropsRef.current = props; void execute("onPropsChange", prev, props); }
// Quota:
context.setState({ quotaReached: reached });   // 新对象 → 必然触发一次重渲染
后果
父组件每渲染一次 → 一次异步钩子链 + 一次 setState → 组件再渲染一次（state 对象变化）；再叠加 P2-4 的 context 重建，列表页的更新成本被放大。
建议
Quota 写入前比较 state.quotaReached === reached；HOC 用浅比较（或由消费方保证 props 引用稳定）后再触发 onPropsChange。

P2-6 · 插槽 key 带 index，且 useImperativeHandle 依赖缺失（lint 已报）

P2
证据
packages/plugin-core/src/react/slots.tsx:44 key={`vane-slot-${plugin.name}-${index}`}；CouponCore.tsx:51 的 useImperativeHandle 依赖只有 [phase]，containerRef 未列入（eslint 报 warning）。
后果
插件数组顺序变化（动态启停/换配置）会让 index 变，React 视为新节点重挂载，插件内部 UI 态（规则展开、复制成功提示）被重置；ref 在外部容器 ref 切换时拿到的 getContainer 可能指向旧节点。
建议
key 只保留 plugin.name（同名插件本就互斥，见 P2-8）；补 containerRef 到依赖数组。

P2-7 · CopyCodePlugin 的定时器与异步无清理，且兜底 API 已废弃

P2
证据
CopyCodePlugin/create.tsx:60-75
context.setState({ codeCopied: ok });
if (ok) config.onCopied?.(code);
window.setTimeout(() => context.setState({ codeCopied: false }), 1600);
后果
卸载后仍会有一次 setState；连续点击会叠加多个定时器，使「已复制」提示提前消失；document.execCommand("copy") 在现代浏览器已废弃，在严格 CSP / 无用户手势下会失败且无提示（onCopied 不触发，按钮文案回到「复制」）。
建议
把 timer 存在 ref 并在 onUnmount 清理；兜底失败时给出可感知的提示（或 onError）；文档标注需要用户手势。

P2-8 · 插件 config 里声明的槽位与真实渲染钩子不一致；Channel 用 label 作 key

P2
证据
ClaimStatePlugin/create.tsx:62、SharePlugin/create.tsx:21、RemindPlugin/create.tsx:24 都把 slotPosition 写成 "after"，但实际实现的是 renderFooter（footer 槽不看 slotPosition）；ChannelPlugin/create.tsx:33-37 key={label}。
后果
配置元数据（doc.json / 插件市场）展示的槽位与实际位置不符，接入方按 slotPosition 推断布局会出错；同一券出现重复渠道标签（如两个「仅 APP」）时 React 报 duplicate key 并可能丢标签。
建议
footer 类插件统一声明 slotPosition: "footer"（或把该字段标注为仅 header 生效）；Channel key 改为 `${label}-${i}`。
05

安全审查（security-best-practices）

结论：没有可利用的注入面。券数据全程走 React JSX 文本，唯一的直接 DOM 操作是复制兜底（写 textarea.value，不解析 HTML），没有 innerHTML / dangerouslySetInnerHTML / eval / new Function（全包 grep 0 命中）。

注入与外部输入

XSS安全title / rules / channels / history.action / code 全部由 JSX 转义；无危险 DOM 写入。
链接低危DetailLinkPlugin 把 config.href 直接给 <a href>（:50-63），带 target="_blank" rel="noreferrer"。若 href 来自后台活动配置而非代码常量，需白名单 https?:；React 会拦截 javascript: 并告警，但 data: 仍可打开。
复制兜底安全隐藏 textarea 通过 ta.value = text 赋值，不拼接 HTML；execCommand 已废弃但无注入风险。
埋点外发低危AnalyticsPlugin 只上报 couponId / phase / message（:39-57），不含用户数据；但 CouponData 带 [key: string]: any 索引签名（types.ts:61），宿主若把整份 coupon 丢进日志，可能把后台附带字段（内部备注、库存策略）一起外发。

凭证与配置面

凭证未发现包内无 token / key / cookie 读写；package.json 仅发布 dist，demo 与测试不进包。
请求宿主职责组件自身不发网络请求，claim / onShare / onEvent 都由宿主注入；CSRF / 鉴权不在本包边界。

成立的部分

状态单一来源正确相位 / 有效期 / 展开态全部落在内核 state（setState 由 useState 驱动），插件不各自持有副本，不存在双向同步。

缺口

事件钩子过频onPropsChange 以引用比较，父组件内联 props 时每次渲染都跑一遍插件链（P2-5）。
初始化语义onMount 用空依赖 + eslint-disable（withPlugins:80-83），StrictMode 下会执行两次（coupon:mount 埋点翻倍）；插件重建时又完全不执行（P1-4）。
