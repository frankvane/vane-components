01

核心数据流与职责边界

图片加载只有一条真实路径：插件在「渲染期」改写 props，在「门控期」决定是否放行，在「事件期」改写 DOM 或上报状态；而状态的唯一权威是 Core 内部的 reducer。下面的 P0 几乎都发生在「事件期」与「权威状态」脱钩的地方。

① props 进入 HOC

withPlugins 在 render 内跑 transformProps（DataSaver / Responsive / BlurUp 等改写 src 与 style）。

② 视口判定

ObserverPool 按 root|rootMargin|threshold 复用实例，回调写 inView。

③ 门控 + 加载链

onBeforeLoad 返回 false 抛 LLI_PLUGIN_GATE；onLoad 可返回替代 src（FetchLoader 等）。

④ reducer 状态机

idle → loading → loaded | error，displaySrc 是唯一渲染源。

⑤ img 事件回流

onLoad / onError → dispatch；插件再执行 onLoadSuccess / onLoadError。

02

已验证成立的核心机制

这些是最容易被误判为 bug、但核对代码后确实成立的部分，不应作为问题上报；修复时应保持其语义。

✓IO 实例共享与 root 身份

ObserverPool 用 WeakMap<Element, string> 给 root 分配稳定 id，key 为 root-rN|rootMargin|threshold；相同配置的 N 张图共用 1 个 observer，root 被 GC 后 id 自动释放。

✓观察器在卸载时确实释放

useIntersectionObserver 的 effect 返回 unobserve()，unobserve 内部同时 observer.unobserve 与删除回调和 elementToKey 映射；不是只 break 掉的假清理。

✓插件按对象引用重注册

plugin-core 用 pluginsSnapshotRef 逐项比较引用（而非 name 字符串），同名换配置能生效，内联数组也不会每次渲染重注册。

✓单插件异常被隔离

transformProps / transformData 对每个插件单独 try/catch，抛错只跳过该插件并 warn；对比 danmaku 早期版本的 P1-4 已修复。

✓门控不污染错误态

LLI_PLUGIN_GATE 被 Core 单独识别：不 dispatch error、不 dispatch loading，占位保持原样，避免「防抖插件一拦就红屏」。

✓loaded 不重设 displaySrc，不闪白

LOAD_SUCCESS 只改 status 并保留 displaySrc；且 img 在 loading 阶段就已渲染，成功时只切 opacity，避免卸载重挂导致的二次请求与闪烁。

✓URL 全部走 new URL / searchParams

DataSaver、CDNFallback、Responsive、MemoryPressure 的查询参数改写都用 URL + searchParams.set，并对非法输入 try/catch；不存在字符串拼接出 query 的注入面。

✓卸载中止 + objectURL 回收

Core 卸载 abort 在途 controller；FetchLoader 的 onUnmount 同时 abortInFlight 与 revokeObjectURL；CachePrewarm 也在卸载时 revoke 自己创建的对象 URL。

03

P0 问题（崩溃 / 错误图片 / 安全，须本迭代修）

四条都能在常规接入方式下被触发；前两条组合起来会让「换图」彻底失效，第三条在弱网/挂 CDN 时表现为无限网络请求。

P0-1 · loaded / loading 态换 src 被守卫直接 return，图片永远不更新

P0
证据 1
src/components/LazyLoadImagePlugin/LazyLoadImageCore.tsx:326-334，startLoad 的两个前置守卫对「已加载 / 加载中」直接返回，且发生在 abort 之前。
const startLoad = useCallback(async () => {
  if (state.status === "loading" || state.status === "loaded") return;   // :328
  if (state.status === "error" && lastAttemptSrcRef.current === src) return;
  lastAttemptSrcRef.current = src;
  if (abortControllerRef.current) abortControllerRef.current.abort();   // 走不到
  ...
}, [src, ..., state.status]);
证据 2
同文件 :384-392 触发 effect 依赖 startLoad（因而 src 变化会重跑），但重跑后仍被同一守卫挡住；Core 内没有任何「src 变化 → RESET / abort」的 effect（全文只有 15 处 src 引用，无监听）。
证据 3
src/components/LazyLoadImagePlugin/withPlugins.tsx:158-165 HOC 对 src 变化只执行 onSrcChange 钩子，既不调用 reset() 也不调用 reload()。
后果
轮播 / 头像 / 虚拟列表复用节点时，已加载或加载中的组件换 src 会一直显示旧图；旧请求完成后 LOAD_SUCCESS 把状态钉在 loaded，新图再也没有机会。只有 error 态换 src 才能侥幸重新加载。
建议
在 useEffect([src]) 中 abort 在途请求并 dispatch RESET，或让守卫比较 state.displaySrc !== src 而非只看 status；补一条「loaded 后换 src 应发起新请求」的回归测试。

P0-2 · img 的 onLoad / onError 不校验请求身份，旧请求事件覆盖新状态

P0
证据
LazyLoadImageCore.tsx:526-545 两个处理器都是「事件一到就 dispatch」，既不看 e.currentTarget.currentSrc，也没有请求令牌或 src 比对。
onLoad={() => {
  ...
  dispatch({ type: "LOAD_SUCCESS" });                 // 不携带 src
  onLoadSuccess?.(state.displaySrc || undefined);     // state 闭包里的旧值
}}
onError={() => {
  const err = new Error("Image load error");
  dispatch({ type: "LOAD_ERROR", payload: { error: err } });
}}
放大器
FallbackImagePlugin/create.ts:14-23、CDNFallbackPlugin/create.ts:42-46、RetryOnErrorPlugin/create.ts:17-20 都是直接改 img.src，不经 reducer；此时 DOM 的 src 与 state.displaySrc 已经分叉，后续事件无从辨别属于哪次请求。
后果
快速换图 / 回退链重试时，旧 URL 的迟到 onLoad 会把新状态置为 loaded 并回调 onLoadSuccess(旧 src)，出现「状态说成功、画面是另一张图」；onError 也可能把已成功的新图打回 error。与 P0-1 组合后，最终展示的往往是最早那张图。
建议
给每次加载分配 requestId，并写入 img.dataset.lliSrc；onLoad/onError 里比较 e.currentTarget.currentSrc 与当前期望 src，不匹配直接忽略；LOAD_SUCCESS 携带 src 并校验。

P0-3 · CDN 回退无次数上限：每次失败都改写 img.src，形成无限重试循环

P0
证据
src/custom-plugins/CDNFallbackPlugin/create.ts:35-47
onLoadError: (context) => {
  if (!bases.length) return true;
  const prev = Number(context.sharedData?.get("cdn-index") ?? 0);
  const next = (prev + 1) % bases.length;          // 只会轮转，永不停止
  context.sharedData?.set("cdn-index", next);
  const img = context.imageRef?.current;
  if (img) {
    const altSrc = swapBase(context.src, bases[next]);
    img.src = `${altSrc}${...}&cdnFallback=${Date.now()}`;   // 每次强制 cache-bust
  }
  return true;
}
后果
所有 CDN 都 404 / 挂掉时，每次 error 都换一个新 URL 再试，没有任何 attempt / max / 停止条件：无限请求、无限日志、持续耗电；Date.now() 还让每轮必然击穿 CDN 与浏览器缓存。若同时启用 RetryOnError，两套机制会并发改写同一个 img.src（RetryOnError:14-20 的 setTimeout 也未被跟踪）。
建议
记录 cdn-attempts 并在 >= bases.length + 1 时返回 false 让错误继续传播；去掉 Date.now() cache-bust（或仅在首次尝试使用）；与 retry 插件互斥（文档 + 运行时检测）。

P0

证据 2

04

P1 问题（真实接入必然踩到）

多为「默认值 / 环境差异 / 钩子链语义」造成的失效，单看是边角，接入后会直接表现为「不加载 / 不刷新 / 缓存不生效」。

P1-1 · 空 src 会永久停在 loading，没有任何出口

P1
证据
LazyLoadImageCore.tsx:359-362 空串照常 dispatch LOAD_START；:506 渲染条件是 {state.displaySrc && ...}，空串为假 → 不渲染 img，因此永远不会触发 onLoad/onError。
const finalSrc = maybeCached || src;
dispatch({ type: "LOAD_START", payload: { src: finalSrc } });   // src === "" 也照发
...
{state.displaySrc && (<img src={state.displaySrc} ... />)}   // "" 被跳过
后果
列表里常见的「暂无图片 / 异步尚未回填」会得到一个永久 spinner（:484-502 的 Loading 提示），既不报错也无法通过 onLoadError 通知业务；父组件容易误以为是网络问题。
建议
在 startLoad 开头对 !src.trim() 直接 dispatch RESET（或进入独立 empty 态）；同时把 {state.displaySrc && ...} 换成显式 status 判断。

P1-2 · 没有 IntersectionObserver 的环境直接抛 TypeError，无降级

P1
证据
ObserverPool.ts:203-204 只判断 observers.has(key)，随后 new IntersectionObserver(...)，没有 typeof IntersectionObserver 检测，也没有 catch。

LazyLoadImageCore.tsx:173-201 该调用发生在 useEffect 里，抛错会沿 React 提交阶段上抛；shouldUseIntersectionObserver（:276-285）只看 LCP/eager，不看环境能力。

P1-4 · root 变化不进 optionsKey，切换滚动容器后仍观察旧 root

P1
证据
LazyLoadImageCore.tsx:165-171 序列化 key 明确排除 root；:173-201 effect 只依赖 optionsKey，而实际传给 IO 的 root 来自 optionsRef.current（:188）。

后果
抽屉 / Tab / Modal 场景中，把 root 从 window 换成内部滚动容器（或容器 ref 从 null 变为真实元素）时，effect 不重跑：元素仍然绑在旧 root 上，表现为「明明在容器里可见却永不加载」或「离开容器仍判可见」。

把 root 加入依赖（对象身份变化才重建，成本可接受）；或用与 ObserverPool 相同的 root 稳定 id 参与 key，避免每次渲染新对象导致抖动。

P1-5 · 门控中止后同一视口周期内不再重触发

P1
证据 1
ViewportDebouncePlugin/create.ts:42-62 进入视口后轮询；若期间离开且未到 maxWait，返回 false。
证据 2
LazyLoadImageCore.tsx:363-372 收到 LLI_PLUGIN_GATE 后仅 return，不 dispatch、不改状态；触发 effect 依赖 [inView, startLoad, shouldUseIO]（:392），在 inView 保持 true 时不会再调用。
后果
快速滚动过去再停下（元素仍停在视口内）时，门控判定「离开」而中止；由于 inView 没有从 true 变 false 再变 true 的跳变（默认 unobserveOnVisible=true，见 P1-3），组件会停在 idle，图一直不加载，也没有 Loading 提示（:484 只在 loading 显示）。
建议
门控中止后设置一个内部 gateEpoch（setState）让 effect 重新尝试，或用定时器按 maxWait 后自动重试；同时让 ViewportDebounce 在「未离开但未稳定」时返回 true 而不是 false。

P1
证据 1
packages/plugin-core/src/manager/PluginManager.ts:105-106 钩子返回非 undefined / 非 true 的值就立刻结束整条链。

证据 2
FetchLoaderPlugin/create.ts:306-316 catch 里也 return url，所以 onLoad 永远返回字符串：FetchLoader 之后的 CacheIDB / ConcurrencyControl / MemoryPressure 的 onLoad 全部不执行。
证据 3
PluginSandbox.ts:17-31 默认 timeout = 3000，Promise.race 超时 reject；PluginManager.ts:76-86 对所有钩子默认启用沙箱。

① 排在 FetchLoader 之后的缓存 / 并发 / 降载插件形同虚设；② 图片在弱网下超过 3s，整个 onLoad 被判超时 → Core 用原始 src 发起 <img> 请求，而 fetch 仍在后台跑完并生成一个永远没人用的 objectURL：同一张图下载两次，且超时后必然进入 error 路径（首屏大图在 3G 下几乎必现）。

P1-7 · performance-first 预设自相矛盾：缓存永不命中 + 每次成功都二次 fetch

P1
证据 1
src/presets/performance-first/index.ts:6-13 顺序为 FetchLoader → CacheIDB → ConcurrencyControl → …；按 P1-6 的短路语义，CacheIDB 的 onLoad 永远轮不到。
证据 2
CacheIDBPlugin/create.ts:211-268 onLoadSuccess 发现 sharedData 没有 fetch-loader:blob 时，主动再 fetch(context.src) 写 IDB。
let blob = context.sharedData?.get("fetch-loader:blob") as Blob | undefined;
if (!blob && !fetchingKeys.has(context.src)) {
  const res = await fetch(context.src, { cache: "force-cache", signal: controller.signal });
  ...
}
后果
全包检索 fetch-loader:blob / fetch-loader:object-url 只出现在 CacheIDB 内，FetchLoader 从不写入 → 命中分支恒假。结果是：FetchLoader 下载一次、CacheIDB 又下载一次（命中 force-cache 时可能走 HTTP 缓存，但仍是完整请求链路），而 IDB 命中永远不会被用来替换 src —— 这个「性能优先」预设实际上比不用更慢。
建议
调整顺序（CacheIDB 在 FetchLoader 之前，命中直接返回对象 URL 并跳过 fetch）；或让 FetchLoader 把 blob 写入 sharedData 供 CacheIDB 复用；同时给预设补一条「二次访问只发生 0 次网络请求」的集成测试。

后果
列表滚动容器反复挂载/卸载（Tab 切换、路由切换）时，每个旧容器都被 Map 强引用且监听仍挂在它上面：DOM 与整棵子树无法 GC，滚动一次还会触发所有历史容器的 handler。属于真实的内存泄漏，不是理论问题。

05

P2 问题（契约 / 性能 / 可维护性）

不影响主链路成立，但会持续拉高接入成本与排障难度；建议随 P1 一起排期。

P2-1 · 默认没有占位比例：CLS 与「模糊图不可见」同时存在

P2
证据 1
LazyLoadImageCore.tsx:439-469 容器默认 height:"auto"；img 默认 height:"auto"（:546-555），加载前容器高度为 0（或仅占位文字高度），加载完成后被自然高度撑开。
证据 2
AspectRatioSpacerPlugin/create.ts:8-23 需要显式启用，且默认 ratio 4/3 与真实图片比例无关；BlurUpPlugin/create.ts:17-43 给 img 加 filter: blur()，但 Core 只在 loaded 时把 opacity 置 1（:552），模糊阶段整张 img 是透明的 → 看不到「先模糊后清晰」。
后果
首屏图片加载完成时兄弟节点被下推（CLS 直接计入 Core Web Vitals）；BlurUp 与 Skeleton/SVG 叠加时还会互相遮挡；接入方以为「内置模糊占位」，实际只有空白。
建议
给 Core 增加可选 aspectRatio / width+height，默认用 aspect-ratio 占位；BlurUp 改为在 loading 阶段把 opacity 设为 1 并配合占位层，或明确文档说明它只作用于已解码图。

P2-2 · Skeleton 每个实例都往 DOM 里插一份全局 keyframes

P2
证据
SkeletonPlugin/create.tsx:57-70 每渲染一个骨架屏就在组件树里塞一个 <style>（不是 @keyframes 去重），注释写「局部作用域」但 @keyframes 本质是全局。
后果
列表 200 张图 → 200 份重复 CSS，动画名全局冲突（后加载的覆盖前者），且每次重渲染都重新解析样式文本。
建议
在模块加载时只注入一次（if (!document.getElementById("lli-skeleton-style")) ...），或改用 background-position CSS 变量 + 已有样式表。

P2-3 · HoverPrefetch 的 image 目标在 onMount 时还拿不到 img；preload link 只加不删

P2
证据 1
HoverPrefetchPlugin/create.ts:102-111 onMount 里取 imageRef.current；但 Core 只有在 state.displaySrc 存在时才渲染 <img>（LazyLoadImageCore.tsx:506），idle 阶段 ref 恒为 null → if (!el) return，target:"image" 的监听永远绑不上。
证据 2
同文件 :28-41 addPreload 只 append 到 document.head，onUnmount（:113-119）只移除事件监听与清空 Set，不删 link。
后果
配置 target:"image" 时功能完全失效且无任何告警；预取链接随浏览会话累积，长列表会留下大量无用的 preload 提示给浏览器。
建议
target=image 改为延迟绑定（imgRef 回调 / effect 轮询一次）；onUnmount 按 id 清理本插件插入的 link。

P2-4 · Responsive 的 srcset 只在成功后补、且 src 已是 blob:，造成二次下载

P2
证据
ResponsivePlugin/create.ts:42-56 只在 onLoadSuccess 里 setAttribute("srcset", ...)，用的 base 是 context.src（原图 URL）；而此时 FetchLoader 已把显示 src 换成 blob:（FetchLoaderPlugin/create.ts:298-305）。
onLoadSuccess: (context) => {
  const base = context.src;
  const parts = variants.map((v) => `${v.src ?? buildSrc(base, v.width)} ${v.width}w`);
  img.setAttribute("srcset", parts.join(", "));
}
后果
第一次加载走 fetch；成功后浏览器看到 srcset，可能再按 DPR/宽度发起一次图片请求，把「省流量」变成「多下载」；src 变化时也没有更新 srcset 的入口（onSrcChange 是空实现，:57-61）。
建议
在 transformProps 阶段就写入 srcset/sizes（核心需透传这两个属性），且当 displaySrc 是 blob:/data: 时跳过 srcset；onSrcChange 里重建。

P2-5 · RetryOnError 的重试计数跨 src 累积，定时器也不可取消

P2
证据
RetryOnErrorPlugin/create.ts:34-39 计数存 sharedData（生命周期内不随 src 重置），:10-21 setTimeout 未保存句柄，onUnmount 也没有清理。
后果
换图后 retry-count 仍为旧值，新图第一次失败就显示「重试失败」；组件卸载后定时器仍会执行 img.src = ...，对已卸载（但 ref 未置空）的节点发起请求，并可能触发 React 之外的状态副作用。
建议
计数以 src 为 key 或写 retry:<src>；保存 timer id 并在 onUnmount/onSrcChange 中 clear。

P2-6 · CacheMemory / CachePrewarm 的 blob: 策略互斥，预热结果永远用不上

P2
证据
CacheMemoryPlugin/create.ts:122-125 命中直接返回 undefined（拒绝 blob: 是为了避免引用已 revoke 的 URL）；CachePrewarmPlugin/create.tsx:57-60 预热写进内存的恰恰是 URL.createObjectURL(blob)。
后果
offline-first 预设里 CachePrewarm 的「进视口即预热」把对象 URL 放进 MemoryCache，而真正读它时被主动丢弃 → 预热只增加一次 fetch + 一个对象 URL 的生命周期负担。若 revoke 发生在读取前，还会得到失效 URL。
建议
内存缓存统一存 Blob（读取时再 createObjectURL 并由 Core 归还），或让 Prewarm 只写 IDB；两条路径只保留一条。

P2-7 · useLCPPreload 把 src 拼进 CSS 选择器，未转义

P2
证据
src/hooks/useLCPPreload.ts:69-80
const existingLink = document.querySelector(
  `link[rel="preload"][href="${src}"]`
) as HTMLLinkElement;
后果
src 含 " / [ / ]（签名 URL、带引号的 CDN 参数）时抛 DOMException: not a valid selector，整个 effect 中断，预加载失效甚至打断同批 effect；已存在的 link 也永远不会被清理（:77-80 直接 return）。
建议
改为遍历 document.querySelectorAll('link[rel="preload"]') 比较 .href；或 CSS.escape(src) 后再拼接。

P2-8 · ObserverPool 单例定时器不停；重复观察时只删掉第一个回调

P2
证据 1
ObserverPool.ts:130-154 构造时启动 setInterval(..., 60000)，只有 disconnectAll() 会停止；作为模块单例，应用生命周期内一直跑。
证据 2
:303-306 Array.from(callbacks).find(...) 只删除第一个同元素回调；:309 随后删除 elementToKey，下一次 unobserve 在 :293 直接 return → 剩余回调无法再被移除。
后果
同一元素被重复观察（StrictMode 双执行、root 变化重建）时，旧回调残留在 observerCallbacks 集合中，每次相交都会重复执行（多次 setState / 多次 enter 钩子）；定时器在测试与 SSR 环境还需要手动 disconnectAll 才能不阻止进程退出。
建议
unobserve 删除全部 cb.element === element 的回调并同步 elementCount；定时器改为惰性启动（有元素时才启动，空闲后 stop）。

P2-9 · GlobalContext 的全局监听在模块单例上永不移除

P2
证据
src/utils/GlobalContext.ts:42-74 initListeners() 挂 connection.change + online/offline + resize，没有任何 removeEventListener 或 dispose。
后果
作为进程级单例，生产环境可接受；但在微前端 / 多次创建 Root / 测试环境里会重复注册（若模块被重新求值），监听器叠加并持有旧回调，无法回收。
建议
提供 globalContext.dispose() 并在文档注明单例边界；connection 的 handler 与 resize 的 timer 也要能清理。

P2-10 · 默认 rootMargin 为 0px：没有任何提前量，首屏边缘图必然「先白后图」

P2
证据
LazyLoadImageCore.tsx:148-153 默认 rootMargin = "0px"、threshold = 0，所以元素像素真正进入视口的那一刻才开始 fetch/赋值 src。
后果
滚动到边界时，加载与网络 RTT 全部发生在用户已经能看到空占位之后，体感是「懒加载很慢」；与 loading="lazy" 的浏览器原生提前量叠加后行为也不一致。
建议
默认给出 rootMargin: "200px 0px"（或按容器高度的一半）作为可覆盖默认；在 README 说明与原生 lazy 的差异。
06

安全审查（security-best-practices）

结论：注入面很小但不是零——唯一 HTML 注入点是 SVG 占位符；URL 侧没有字符串拼接，但也没有协议/域名白名单。数据出站方面，错误上报插件会把图片地址与堆栈发往配置端点。

注入与 URL

XSSP0SvgPlaceholderPlugin/create.tsx:77 的 dangerouslySetInnerHTML 是全包唯一 sink；配置来源不可信即存储型 XSS（P0-4）。
其他 HTML安全grep innerHTML / eval / new Function 无其他命中；Skeleton 注入的 <style> 为静态常量。
URL 拼接安全DataSaver / CDNFallback / Responsive / MemoryPressure 均用 new URL + searchParams，并对失败回退，无拼接注入。
协议白名单低危未限制 scheme / host：data:、blob:、任意外域都会原样进入 img.src；javascript: 在 <img> 上不会执行（现代浏览器），但会把非预期请求/数据带出。建议只放行 http(s)/data:image/blob:。
选择器注入低危useLCPPreload.ts:73-75 用 src 拼 querySelector，特殊字符抛异常（P2-7）；preloadBadge.tsx:13 的 prefix 为代码常量，安全。

数据出站与拒绝服务

错误上报注意ErrorTrackingPlugin/create.tsx 把 src、stack、网络与设备信息 POST 到 reportEndpoint。签名 URL 可能含 token；需在文档中要求过滤 query 并征得同意。
下载插件信息DownloadButtonPlugin/create.tsx 直接 fetch(src) → blob → a.download；跨域需 CORS，失败路径需确认不会把错误吞掉。
无限请求P0CDNFallback 无上限重试（P0-3）本身构成客户端 DoS / 流量放大；Date.now() cache-bust 让 CDN 缓存完全失效。
插件沙箱双刃3s 超时可防止插件钩子卡死宿主（正向），但对 FetchLoader 这类网络钩子会误杀（P1-6）。
凭证安全src 内无硬编码 token；本包未发现提交到仓库的密钥。示例 URL 均为占位域。
07

React / 性能审查（vercel-react-best-practices）

骨架在「生命周期正确 / 清理到位」上做得不错；主要缺口是 effect 依赖语义（root 排除、state.status 进入依赖导致的自动重试兼容）与 渲染期副作用。

成立的部分

监听清理正确IO 观察、progress 订阅、全局上下文订阅、HoverPrefetch 事件都在 effect cleanup 或 onUnmount 中显式解除（P1-8 的 ScrollIdle 是例外）。
卸载中止正确Core useEffect(() => () => abort(), [])（:395-402）；FetchLoader 的 onUnmount 同时 abort + revoke。
memo 使用基本正确容器样式 / finalLoading / finalFetchPriority 都有 useMemo 且依赖完整；plugin-core 的 context 依赖 props/data/state 等真实输入。
状态更新正确reducer 是纯函数，LOAD_SUCCESS 保留 displaySrc，避免 loaded 时换元素造成二次请求（:54-59）。
重复请求抑制设计合理img 在 loading 阶段即挂载（:504-506），成功后只切 opacity，符合「避免卸载重挂」的建议。

缺口

effect 依赖optionsKey 故意排除 root（P1-4）；startLoad 依赖 state.status 使触发 effect 在每次状态流转时重跑——这是「error 自动重试」补丁的副作用，也让 P0-1 的守卫更难绕开。建议用 ref 读 status，触发 effect 只依赖 [inView, src, shouldUseIO]。
渲染期写 refplugin-core/usePluginRuntime.ts:159 在 render 体内执行 contextRef.current = context；并发渲染下可能读到未提交的中间 context（与 danmaku 同一类问题）。
无谓 effectLazyLoadImageCore.tsx:160-162 每次渲染都对 optionsRef 重新赋值（无依赖数组）；可合并到 layout effect 或用 useLatest。
渲染期计算HOC 在 render 内跑整条 transformProps 链（withPlugins.tsx:252-253），无 memo；插件多时每次重渲染都重复构造 style/src 对象。建议以 [props, plugins] 做 useMemo。
图片解码DecodeAfterIdle 只设置 decoding="async"，并未真正在 idle 调 img.decode()；对首屏大图的实际收益有限（需浏览器实测）。
布局抖动AspectRatioSpacer 在 onMount 里直接写 container.style.aspectRatio（:15-21），首帧先以 0 高度绘制再被 effect 修正，会引入一次额外布局。
