01

核心数据流与职责边界

主链路是一条单向流水线：文件描述符进装配层 → 纯函数路由选出唯一赢家 → Core 状态机开门 → 赢家插件动态加载解析库并自报状态 → 工具栏/正文双插槽渲染。 「状态」只有一个真源（Core 的 stateRef），插件只能通过 reportState 上报； 「跨插件通信」只有一张 sharedData。后文所有问题都能落回这两个单点。

① FileInfo 进入装配层

name / type / extension / size / url 由消费方传入，withPlugins 用它做路由与渲染。

② resolvePreview 单赢家

排序键：priority 降序 → 匹配置信度（MIME=2 / 扩展名=1）→ 声明顺序；canHandle 优先且互斥。

③ Core 开门

loading → onBeforeLoad() → loaded / error；无赢家时装配层返回 false 直接落 idle。

④ 插件懒加载解析库

useDynamicModule 动态 import；缺失的 optional peer 落到 MissingDependency 面板，不白屏。

⑤ 双插槽渲染

renderToolbar + render 只渲染赢家；工具栏与正文通过 sharedData + forceUpdate 同步。

已验证成立的核心机制

这几条是最容易被误判为「没做」的地方。逐条按代码与测试核对后结论是「成立」，不作为问题上报。

✓单赢家路由可单测、规则无歧义

resolvePreview 先过滤出 strength > 0 的候选，再按 priority → 置信度 → 声明顺序稳定排序；空 MIME 靠扩展名兜底，不会出现「空 type 一律不认」。test/resolve.test.ts 覆盖通配、互斥、平手、兜底。

✓未知类型有明确的降级面板

无任何插件认领时 onBeforeLoad 返回 false（withPlugins.tsx:217-223），Core 不进加载流程，正文换成 UnsupportedNotice（data-vfp-unsupported，:59/:256）。不会白屏、不会无限 loading。

✓懒加载有卸载守卫

shared/useDynamicModule.ts:43-63 中 let alive = true + cleanup 置 false，模块 resolve 后先判 alive 再写 state；默认导出用 defaultOf 兼容 CJS/UMD。

✓缺依赖可渲染，而不是模块图炸裂

7 个重依赖插件改动态 import，失败落到 shared/panels.tsx:138-241 的 MissingDependency：写明包名、安装命令、折叠原始错误。optional peer 的语义因此成立。

✓Markdown 默认不解析原始 HTML

allowHtml 默认 false（MarkdownPreviewPlugin/create.tsx:530），安全档只加载非 raw 链路；开启档也追加 stripDangerousAttrs 剥 on* 与 javascript:（:159-178 / :343-347）。

✓预览侧不创建 objectURL

全库 URL.createObjectURL 仅 2 处，都是用户触发的导出下载（JsonPreviewPlugin:312-315、CsvPreviewPlugin:193-196），且都在 2s/10s 后 revokeObjectURL。预览本身直接用 file.url，不存在「每渲染一次泄漏一个 blob」。

✓体积门控已有可复制范式

JSON 在 fetch 前用 file.size 拦（JsonPreviewPlugin/create.tsx:172-180），XML 同理（XmlPreviewPlugin/create.tsx:159-167），超限给「下载原文件」的出路而不是硬解析。

✓EPUB 不用 blob URL、关闭脚本内容

EpubPreviewPlugin/create.tsx:385-408 直接把解析后的对象传给 Reader，epubOptions={{ allowScriptedContent: false }}（:394）；文件头注释也记录了「blob: 会丢章节相对路径」的原因。

✓Core 单真源 + 用户回调不丢

FilePreviewCore.tsx:132-136 每次提交都写 stateRef 并回调；withPlugins.tsx:243-252 先做值比较镜像，再把用户的 onStateChange 转发出去，宿主不会「一直停在 idle」。

✓CSV 编码识别是完整的

CsvPreviewPlugin/parse.ts:170-212：BOM → 严格 UTF-8 → GB18030 → 宽容 UTF-8 四级降级，避免 GBK 表格一片乱码；parseCsv 还补齐长短行并给出 warnings。

P0-1 · PDF / Office 用无 sandbox 的 iframe 渲染不受信文件

P0
证据 1
packages/vane-file-preview/src/custom-plugins/PdfPreviewPlugin/create.tsx:89-90
{useIframe ? (
  <iframe src={src} title={file.name} style={frameStyle} />
) : (
  <embed src={src} type="application/pdf" style={frameStyle} title={file.name} />
)}
证据 2
packages/vane-file-preview/src/custom-plugins/OfficePreviewPlugin/create.tsx:206-210 同样是裸 <iframe src={buildViewerUrl(...)}>。全库 src 检索 sandbox 命中数为 0。
证据 3
PDF 插件同时声明了 supportedTypes: ["application/pdf"] 与 supportedExtensions: [".pdf"]（PdfPreviewPlugin/create.tsx:61-62）。matchExtension 命中即得 1 分置信度，因此只要扩展名是 .pdf，即使 MIME 声明不对也会被路由到 PDF 插件。
后果
文件预览的输入天然不可信（用户上传、别人转发的链接）。当 iframe 目标实际返回 text/html（同源静态目录、按扩展名给 MIME 的简易文件服务、或消费方自建的 blob: URL —— blob 继承创建者 origin）时，HTML 里的脚本会在宿主源执行，可读 cookie/localStorage、代发同源请求，构成存储型 XSS。若目标跨源，脚本虽被 SOP 隔离，但仍可诱导点击/社工。Office 走第三方 viewer，风险低一档，但同样缺失边界。
前提
浏览器对真正的 application/pdf 会进内置查看器、不执行 HTML；本条的触发条件是「响应 Content-Type 为 HTML 而路由仍按扩展名命中」，属于真实可达但非默认路径。这里按「安全边界缺失」定级 P0。
建议
给两个 iframe 加 sandbox="allow-scripts"（不要同时给 allow-same-origin，否则可逃逸到宿主源）或更严格的 sandbox=""，并配 referrerPolicy="no-referrer"；PDF 场景更彻底的做法是引入 pdf.js 自绘，不走 iframe。服务端/消费方配合设置 Content-Security-Policy: frame-src 白名单与 X-Content-Type-Options: nosniff。改动后需回归「内置 PDF 查看器是否仍可翻页」。

P1-1 · 加载状态无请求令牌：快速切文件时旧加载覆盖新文件

P1
证据 1
packages/vane-file-preview/src/components/FilePreviewPlugin/core/FilePreviewCore.tsx:145-172
const runLoad = useCallback(async (opts?: { force?: boolean }) => {
  const cur = stateRef.current.state;
  if (!opts?.force && (cur === "loading" || cur === "loaded")) return;

  commit({ state: "loading" });
  try {
    const canLoad = await Promise.resolve(callbacksRef.current.onBeforeLoad?.());
    if (canLoad === false) { commit({ state: "idle" }); return; }
    commit({ state: "loaded" });
  } catch (error) { commit({ state: "error", ... }); }
}, [commit]);
证据 2
同文件 :181-184 自动加载 effect 只依赖 file.url，没有 cleanup：useEffect(() => { void runLoad({ force: true }); }, [file.url])。
时序
文件 A 的 onBeforeLoad 是异步的（比如消费方在那里取签名 URL / 做鉴权），此时用户切到文件 B：B 的 runLoad 先 commit(loading)，随后 A 的 Promise resolve → commit(loaded) → A 的进度把 B 的状态改成 loaded，而 B 的内容可能还没开始渲染。反向（A 抛错）则会把 B 打到 error。
同类
插件里旧异步任务在文件切换后仍调 reportState（如图片 onError），同样会写入新文件的状态 —— Core 只校验补丁内容，不校验「这条上报属于哪个文件」。
建议
引入 loadTokenRef：每次 runLoad/reportState 携带当前 token（或 file.url 快照），每个 await 后与最新 token 比对，不一致直接丢弃；effect 的 cleanup 递增 token。插件侧异步也能复用同一个 token。

P1-2 · DOCX 渲染竞态：fetch 之后、渲染之前没有 alive 检查

P1
证据
packages/vane-file-preview/src/custom-plugins/DocxPreviewPlugin/create.tsx:115-133
const res = await fetch(file.url);
...
const arrayBuffer = await res.arrayBuffer();

const host = hostRef.current;
if (!host) return;
host.innerHTML = "";                       // 旧内容先清空
await docx.renderAsync(arrayBuffer, host, null, {...});
if (!alive) return;                         // 只有渲染完才检查
setState({ status: "ready" });
问题
cleanup 只把 alive = false，但代码在清空 DOM 与 renderAsync 之间从不读它。切到文件 B 后，A 的 fetch 若更晚 resolve，旧 effect 仍会清空 host 并把 A 的文档画进 B 的容器 —— 表现为「切过去先看到旧文档，再被新文档覆盖」或直接停在旧文档。
建议
在 fetch、arrayBuffer、DOM 清空之前各补一次 if (!alive) return；fetch 传 AbortController。更稳的写法是先渲染到游离的 DocumentFragment/临时节点，完成后再整体替换 host，避免半成品文档闪入。

P2-4 · 图片缩放没有平移，高倍缩放只能看中心

P2

P2-8 · 工具栏按钮绕过 React 直接改 DOM 样式，图标按钮无 aria-label

P2
证据
shared/ToolbarComponents.tsx:134-147
onMouseEnter={(e) => {
  if (!disabled && !active) {
    Object.assign(e.currentTarget.style, baseStyle, toolbarStyles.buttonHover);
  }
}}
onMouseLeave={(e) => {
  if (!disabled && !active) Object.assign(e.currentTarget.style, baseStyle);
}}
问题 1
直接写 style 绕过了 React 的 style diff：一旦某个按钮由 active 变回 false，React 只会 diff 它认为变化的键，鼠标态残留可能与 state 打架。正确做法是 useState(hovered) 或 :hover 类。
问题 2
按钮只传 title，没有 aria-label；多个插件用的是 emoji 图标（如 🔍、⬇），读屏软件会把 emoji 当正文念，语义丢失。
建议
hover 态改为 React state；ToolbarButton 增加 aria-label 必填项（缺省取 title），图标 span 加 aria-hidden="true"。

安全审查（security-best-practices）

输入模型：文件内容不可信，文件名/URL 也不可信。审查口径是「不受信内容进入 DOM / iframe / 剪贴板 / 第三方服务」的每一处边界。 总体：Markdown 与 EPUB 两道高风险面收得很紧；DOCX/XLSX 与 PDF 三道面偏松。

注入面盘点（全库检索）

dangerouslySetInnerHTML2 处：MammothDocxPlugin:182、XlsxPreviewPlugin:265 —— 均无本地清洗 P1-5
innerHTML1 处：DocxPreviewPlugin:122，写入内容来自 docx-preview 的 DOM 渲染，不是字符串拼接
iframe2 处：PDF 与 Office；sandbox 命中 0 P0-1
createObjectURL2 处，均为导出下载，2s / 10s 后 revoke 成立
eval / new Function无命中
sanitize 依赖全库无 dompurify / sanitize-html / xss 缺位

已收口的边界

Markdownraw HTML 默认关闭；开启档追加 stripDangerousAttrs 剥 on* 与 javascript:；链接统一加 noopener noreferrer 安全默认
URL 协议Markdown 图片/链接走 SAFE_PROTOCOLS 白名单（MarkdownPreviewPlugin:191-208） 成立
EPUBallowScriptedContent: false，且刻意不用 blob URL（避免相对路径失效与 origin 继承） 成立

隐私代码偏好 localStorage 有 vane-file-preview: 前缀、storage:false 可关、字段做合法性校验（preferences.ts:60-140） 成立
CSP组件库不设响应头；消费方需自行配 frame-src / object-src 部署侧

iframe 与 URL 生命周期

PDF src直接 file.url + hash 参数（PdfPreviewPlugin:42-48），不校验协议：javascript: URL 不会被 iframe 执行为脚本（浏览器拒绝），但 data:text/html 会。
Office src先过 isPubliclyReachableUrl，再 encodeURIComponent 拼 viewer IPv6 漏判 P2-9
EPUB 历史文件头注释明确记录「曾用 blob:，因相对路径丢失而弃用」—— 这个取舍反而消掉了一个 URL 生命周期问题。
预览 URL库本身从不创建预览用 objectURL，故不存在「组件卸载后 blob 仍存活」的泄漏；file.url 的 revoke 责任在消费方。
建议在 README 明确「file.url 由调用方生命周期管理」，并给出 useEffect revoke 示例，避免消费者误以为组件会清。

mammothDOCX → HTML 由库生成，直接 innerHTML；超链接/图片协议未在本地复核 未确证

papaparse / jszip只做解析不产出 HTML，风险面小；但 JSZip 全量解压有性能问题（P1-4）
