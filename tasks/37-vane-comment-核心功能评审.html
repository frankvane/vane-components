01

核心数据流与职责边界

评论区是典型的「受控列表」：组件不做本地列表状态，所有增删改都通过 props 回调交给消费方（演示站 Harness 就是自己 setComments 后重渲染）。 数据在 withCommentPlugins 里走「变换 → 排序」两步后才交给 CommentCore，逐条渲染再经领域槽交给插件。

① 数据接入

props.comments ?? props.data；runtime 的 data 也取同一份原始列表。

② transformData

按 priority 顺序跑：Moderation（脱敏/隐藏）→ Filter（筛选）→ Search（检索）。

③ sortComments

纯函数、[...data] 副本；newest / oldest / mostLiked / hottest / custom。

④ 列表渲染

CommentCore 用 key={comment.id} 渲染，逐条读 renderCommentActions / renderNested。

⑤ 交互回写

点赞/回复/发布/置顶只调用 context.props.onXxx，由消费方更新数据后重新下发。

02

已验证成立的核心机制

这 8 条最容易在评审里被误判成 bug，逐条核对代码与自测断言后结论是「成立」，不应上报。

✓transformData 是真接入的（与 card 不同）

withCommentPlugins.tsx:108-117 显式调用 runtime.transformData(baseData)，并把结果写回 props.data 与 props.comments（:119-124）。Moderation / Filter / Search 都靠它生效，自测「审核：敏感词被脱敏」断言通过。

✓comments 覆盖顺序统一

历史上「只填 data 而消费方传了 comments 导致排序失效」的坑已修：withCommentPlugins:119-124 同时覆盖两个字段，CommentCore.tsx:43-44 读 comments ?? data ?? []，两条路径拿到同一份排好序的列表。

✓排序是纯函数且不改入参

sort.ts:16 用 const arr = [...data] 复制后排序，mode === "custom" 直接返回原数组（:15）；自测用 newest / oldest 分别断言首条作者，证明排序真的驱动了渲染。

✓列表 key 稳定

CommentCore.tsx:107-109 用 key={c.id}，排序后只是位置变化，不复用错节点；ThreadView 的展开态、ReplyTrigger 的输入框位置都随 id 保留。

✓单向数据流，组件不改 comments

LikePlugin 只调 onLike(id,next)（LikePlugin:28-35）、ThreadPlugin 只调 onReply（:285-291）、RichComposer 只调 onSubmit（:86-95）。自测的 Harness 真改 state 后，点赞计数能从 0 变 1，说明链路闭环。

✓逐条插槽有异常隔离

plugins/slots.tsx:71-92 对每个插件单独 try/catch，再包一层 PluginErrorBoundary；某个插件渲染抛错只丢自己那个按钮，不会拖垮整条评论。

✓无 HTML 注入面

content.tsx:8-51 把 text / emoji / image / mention 全部渲染成 React 节点（mention 也只是 {`@${name}`} 文本），全包无 dangerouslySetInnerHTML，评论正文不经过任何 HTML 解析。

✓默认排序只在缺失时播种

SortPlugin:76-84 仅当 state.sortMode 与 props.defaultSortMode 都为空才写 defaultMode，不会覆盖消费方传入的默认模式；extendContext:50-53 的兜底顺序与之一致。

03

P1 问题（核心交互 / 真实接入必踩）

三条都发生在「楼中楼能不能正确显示」与「发布能不能可靠提交」上；现有自测只覆盖两层嵌套与成功路径，因此全绿也不代表这三条不成立。

P1-1 · ThreadPlugin 的 depth 恒为 1：maxDepth 形同虚设，深层/循环 replies 会递归到栈溢出

P1
证据 1
packages/vane-comment/src/custom-plugins/ThreadPlugin/create.tsx:69 —— 限深判断依赖传入的 depth。
const nestedSlot = useCommentSlot("renderNested", reply);
const deeper = depth < maxDepth ? nestedSlot : [];   // depth 必须递增才有意义
证据 2
同文件 :161-169 —— <ReplyNode depth={depth}> 只是把同一层深度继续往下传。
证据 3
同文件 :316-325 —— renderNested 每次都给 ThreadView 写死 depth={1}，而 ReplyNode 又是通过 useCommentSlot("renderNested") 重新进入这个钩子。
renderNested: (context, comment) =>
  comment.replies?.length ? (
    <ThreadView comment={comment} depth={1} maxDepth={maxDepth} ... />   // ← 恒为 1
  ) : null,
后果
递归链是 CommentItem → renderNested → ThreadView(depth=1) → ReplyNode(depth=1) → useCommentSlot("renderNested") → ThreadView(depth=1)…，depth 永远停在 1，depth < maxDepth 恒为真：① maxDepth:3 的配置完全不生效，10 层嵌套会全部展开渲染；② 若数据里出现自引用/环形 replies（后端去重 bug、缓存对象复用、构造测试数据时都可能），递归无终止 → RangeError: Maximum call stack size exceeded，整段回复区被 PluginErrorBoundary 兜成 null（packages/plugin-core/src/sandbox/PluginErrorBoundary.tsx:30-33 且不会自愈），用户看到「回复突然全没了」且无报错。演示站只造了两层数据，自测「楼中楼：含嵌套回复（≥2）」不会暴露。
建议
把深度作为 payload 一起传：useCommentSlot("renderNested", { comment: reply, depth: depth + 1 })，并让 renderNested 读 payload 的 depth 而不是写死 1；或在 ReplyNode 里直接渲染 reply.replies（depth + 1），不再绕回插件钩子。补测试：6 层嵌套在 maxDepth:3 下只渲染 3 层。

P1
证据 1
packages/vane-comment/src/custom-plugins/ModerationPlugin/create.tsx:56-59 —— 只对顶层评论的 content 调 maskNodes，没有递归 replies，也没有处理 c.text。
return arr.map((c) => ({
  ...c,
  content: maskNodes(c.content ?? [], words),   // replies / text 未处理

证据 2
packages/vane-comment/src/components/CommentPlugin/CommentCore.tsx:226-228 —— 正文渲染有纯文本回退：comment.content?.length ? renderCommentContent(comment.content) : comment.text。
证据 3
packages/vane-comment/src/custom-plugins/ThreadPlugin/create.tsx:90-94 —— 嵌套回复同样走 reply.content?.length ? renderCommentContent(reply.content) : reply.text。
后果
① 楼中楼里的「加微信 / 广告」原样显示——审核对最常被滥用的位置完全失效；② 历史数据或简化接入只传 text 时，content 为空数组，maskNodes 拿到空数组 → 完全没脱敏，然后 CommentCore 回退渲染原始 text；③ hidePending 也只过滤顶层，pending / deleted 的回复仍会在 ReplyNode 里出现（:70, 88-89 只做了「已删除」文案，pending 没有特殊处理）。自测只造了顶层 content（demo/src/lib/selftest.tsx「审核：敏感词被脱敏（广告/加微信 不再出现）」），所以通过。
建议
抽 maskComment(comment, words)：递归处理 replies，并对 text 做同样的字符串替换；更好的做法是把脱敏放到渲染出口（renderCommentContent 内部或统一的 safeText()），这样无论哪条渲染路径都绕不过去。补测试：嵌套回复里的敏感词也必须变成 **。

P1-3 · RichComposer 发布无提交态：失败丢草稿、快速双击重复提交

P1
证据 1
packages/vane-comment/src/custom-plugins/RichComposerPlugin/create.tsx:86-95 —— 同步调用 onSubmit 后立刻清空，不等待、不判返回值、不捕获异常。
const submit = () => {
  if (!canSubmit) return;
  context.props.onSubmit?.(preview);   // 可能是 async / 可能抛错
  setText("");
  setImages([]);                       // 草稿已不可恢复
};
证据 2
同文件 :248-264 —— 按钮 disabled={!canSubmit}，只依赖同步的内容判断，没有任何 submitting 状态。
后果
真实接入的 onSubmit 一定是网络请求：① 请求失败（限流 / 未登录 / 审核拒绝）时草稿已被清空，用户只看到内容消失，无法重试；② onSubmit 返回 Promise 期间按钮仍可点，快速双击会提交两条相同评论（也正是 P1-2 脱敏之外最容易被用户投诉的行为）；③ 图片以 DataURL 塞进内容，失败重发时体积更大。自测 Harness 的 onSubmit 是同步 setComments，所以从未进入失败/双击分支。
建议
加 const [submitting, setSubmitting]：await Promise.resolve(onSubmit(...)) 成功后再清空，失败 catch 保留草稿并给提示；按钮 disabled={!canSubmit || submitting}，文案切到「发布中…」。若 onSubmit 契约确实是同步（仅回调），则在类型上明确并要求消费方不能 Promise，同时在文档说明重试语义。
04

P2 问题（契约 / 成本 / 生命周期）

这些不影响「能不能点」，但会在长列表、弱网、多次排序后逐步暴露，并抬高第三方插件的接入成本。

P2-1 · 每次渲染全量重跑流水线并重建新数组，逐条插槽再遍历一次插件

P2
证据 1
packages/vane-comment/src/components/CommentPlugin/withPlugins.tsx:108-117 —— transformData + sortComments 写在渲染函数体内，无 memo、无脏检查。
const baseData = (runtime.context.data as any[]) ?? [];
const transformed = runtime.transformData(baseData) ?? baseData;   // 每次渲染全量
const sortedComments = sortComments(transformed, mode);            // 每次渲染新数组
证据 2
同文件 :136-139 —— const domainContext = { ...runtime.context, comments: sortedComments } 每次渲染都是新对象，CommentSlotProvider 的 useMemo([orderedPlugins, context])（plugins/slots.tsx:42-45）因此恒失效。
证据 3
CommentCore.tsx:155-156 每条评论都调用两次 useCommentSlot，而 renderCommentSlot（slots.tsx:60-71）每次都要 [...plugins].filter().sort()。
后果
点一次排序（或父级任意 state 变化）都会：全量脱敏/过滤 + 全量排序 + N 条评论 × 2 次「复制数组 + filter + sort + 逐插件渲染」。1000 条评论 × 17 插件 ≈ 3.4 万次函数调用/次渲染，且无虚拟化（:107-110 全量 map）。评论少时无感，运营后台的长列表会明显卡。
建议
用 useMemo([props.comments, props.data, orderedPlugins, state.filter, state.query, sortMode]) 缓存 transformed / sortedComments / domainContext；renderCommentSlot 的排序结果按 orderedPlugins 缓存；长列表接 content-visibility:auto 或按需分页。

P2-2 · 领域上下文里的 context.data 仍是原始列表：注释承诺「统一套用」与实现不一致

P2
证据 1
packages/vane-comment/src/components/CommentPlugin/withPlugins.tsx:7-9 的文件头注释写着「plugin-core 提供了 transformData 但运行时不会自动套到 context.data，这里统一套用」。
证据 2
同文件 :108-117, 136-139 —— 实际只覆盖了下发给 CommentCore 的 comments 与 domainContext.comments；{ ...runtime.context } 里 data 字段保持原样（runtime.context.data 来自原始 props.comments ?? props.data，:66）。
对照
CountPlugin:21 读的是 context.comments，所以计数正确（能随筛选变化）；但任何读 context.data 的插件拿到的是未过滤、未脱敏、未排序的列表。
后果
第三方插件按「context.data 是当前可见列表」的直觉写逻辑（导出、批量操作、二次过滤）会看到被 Moderation 隐藏的 pending 评论和未脱敏文本，形成审核旁路与数据泄漏；同一个 context 里 data 与 comments 语义分裂，是维护期的隐性坑。
建议
在 domainContext 里把 data 也替换为 sortedComments（或在类型注释里明确 data = 原始、comments = 可见），并统一在文档与 CommentPluginContext 注释里写明。

P2-3 · Pin / Favorite 用本地 state 初始化一次，与 props 不再同步

P2
证据
packages/vane-comment/src/custom-plugins/PinPlugin/create.tsx:27-31 与 FavoritePlugin/create.tsx:27-31 都是 useState(!!comment.pinned) / useState(!!comment.favorited)，点击时先本地切换再回调。
const [pinned, setPinned] = useState(!!comment.pinned);
const handle = () => { const next = !pinned; setPinned(next); onPin?.(comment.id, next); };
后果
服务端拒绝置顶（权限不足 / 网络失败）时消费方不会回传新 pinned，按钮仍停在「📌取消置顶」，而 CommentCore:197-209 的置顶标从未出现——同一个状态在两处显示相反结论。列表重新下发（轮询/刷新）时按钮也不会跟随新 props，除非组件重挂。
建议
改为「受控 + 乐观回退」：useEffect(() => setPinned(!!comment.pinned), [comment.pinned]) 让 props 为准；或直接不使用本地 state，靠消费方回传（与 LikePlugin 的 liked = !!comment.liked 一致）。

P2-4 · Copy / Share 复制失败仍提示「已复制」，且复位定时器不清理

P2
证据 1
packages/vane-comment/src/custom-plugins/CopyPlugin/create.tsx:34-41
try { await navigator.clipboard?.writeText(plainText(comment)); } catch { /* 静默 */ }
setCopied(true);                              // ← 失败也报成功
window.setTimeout(() => setCopied(false), 1500);   // ← 无卸载清理
证据 2
packages/vane-comment/src/custom-plugins/SharePlugin/create.tsx:24-31 同一模式；另外 navigator.clipboard?. 在 http 非 localhost 环境下是 undefined，可选链会静默跳过。

P2-5 · 点赞爆裂动画定时器不清理；同时点赞数与本地反馈完全依赖消费方

P2
证据 1
packages/vane-comment/src/custom-plugins/LikePlugin/create.tsx:28-35 —— window.setTimeout(() => setBurst(false), 450) 没有清理。
证据 2

P2-6 · 相对时间只算一次，长驻页面里「刚刚」永远不变

P2
证据
packages/vane-comment/src/components/CommentPlugin/content.tsx:54-67 —— formatRelativeTime(ts, now = Date.now()) 在渲染时求值；调用点 CommentCore.tsx:210-211、ThreadPlugin:83-85 都不带 now，也没有任何定时器驱动重渲染。
后果
评论区常驻（信息流浮层、直播弹幕式详情页）时，一条 59 秒前的评论会一直显示「刚刚」，几小时后仍是旧文案；用户会以为列表没刷新。对「时间感」敏感的产品是可见缺陷。
建议
提供一个低频 tick（如 60s 一次，仅当组件可见时），把 now 通过 TimestampPlugin / 上下文下发；或至少让 TimestampPlugin 承担自动刷新，Core 内的相对时间仅在父级重渲染时更新（并在文档说明）。

P2-7 · 富编辑图片走 DataURL 且无类型/大小/数量约束

P2
证据 1
packages/vane-comment/src/custom-plugins/RichComposerPlugin/create.tsx:103-111 —— FileReader.readAsDataURL(file) 把整个文件读成 base64 字符串塞进 images state。
证据 2
同文件 :230-234 —— accept="image/*" 只约束文件选择器，用户拖拽/改扩展名都能绕过；没有任何 file.size / MIME 判断，也没有张数上限。
后果
一张 10MB 照片经 base64 膨胀约 13MB 常驻内存，并随 onSubmit 一次性提交；长会话/多次选择会累积，移动端直接 OOM。DataURL 还会进入评论内容（content.tsx:24-39 渲染为 <img src=data:…>），服务端若不二次校验，等于接受任意内联媒体。
建议
在 onFile 里做三层校验：MIME 白名单（image/jpeg,png,gif,webp）、maxSize（如 5MB）、maxCount（如 9 张）；更好的做法是交给消费方上传拿到 URL（插件只负责收集 File），并在文档写明服务端必须再校验。
05

安全审查（security-best-practices）

结论：没有可利用的代码注入面；但「审核可绕过」是内容合规风险，需要单列。

注入与输出

XSS安全评论正文全部走 React 节点渲染（content.tsx:8-51），mention 也只输出文本；全包无 dangerouslySetInnerHTML / innerHTML / eval。
图片节点注意image 类型直接使用 node.url 作为 src：data: / blob: 都能通过，且不校验来源；javascript: 在 img 上不执行，但仍建议白名单。
剪贴板安全Copy / Share 只写剪贴板，不读取；链接用 location.origin + pathname，不含用户输入。
凭证安全包内无 token / cookie / localStorage 访问；登录态完全由 onLogin / LoginPromptPlugin 交给消费方。

内容合规与第三方能力

审核绕过需修P1-2：嵌套回复与 text 回退不脱敏。涉及 UGC 合规，不能只靠「前端遮一下」——服务端仍须独立审核。
大对象低危P2-7：DataURL 无大小上限，属于前端可触发的内存放大面（用户自己就能把自己页面撑爆）。
第三方插件注意插件 onMount 能拿到容器并可任意 DOM 操作；renderXxx 返回字符串会被 React 转义，但 renderFooter 可返回任意 JSX（含外链）。接入第三方插件需明确信任边界。
建议脱敏改成「渲染出口统一处理 + 服务端二次校验」；图片加域名白名单与体积上限；在 README 明确第三方插件的信任假设。
06

React / 性能审查（vercel-react-best-practices）

按「受控组件的单一数据源 / 避免无谓渲染 / effect 与定时器生命周期」三条主线核对。

成立的部分

受控设计正确组件不维护评论列表状态，所有写操作都回传给消费方，避免了「内部列表与服务端列表分叉」这类最难排查的问题。
key 与复用正确key={comment.id}（CommentCore:108），排序只换位置不换身份；插件返回的节点也有稳定 key（slots.tsx:79-81）。
纯函数正确sortComments 用副本排序、renderCommentContent 无副作用、maskNodes 返回新对象；数据流水线本身是纯的（只是缺 memo）。
