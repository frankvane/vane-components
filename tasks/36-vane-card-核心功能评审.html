01

核心数据流与职责边界

卡片有两条并行入口：插件体系（withPlugins(CardCore, { plugins })，状态在 usePluginRuntime 的 state + PluginBus）与 复合组件体系（ProductCard 的 useProductCard() context）。两者都读写同一份 data，但状态互不可见——这是 P1-4 的根因，也是后面几条价格问题的定位坐标。

① 数据接入

消费方传 data（price / variants / inventory / image）与 plugins；ProductCard 再按插件名记忆 Core。

② 上下文与状态

extendContext 叠加 cardId/data/size/bus；运行时 state = isVisible/isHovered/cart…。

③ 派生键

SKU 选择写 skuVariant / skuPrice / skuImage，数量写 quantity，券写 couponApplied。

④ 渲染

composeSlots 五段（before → children → overlay → after → footer）+ 价格区领域槽。

⑤ 交互回写

控件 bus.setData；setupForceUpdateOnBusKeys 订阅后 forceUpdate 重渲染。

02

已验证成立的核心机制

以下几条是最容易误报的地方：按代码与回归用例逐条核对后结论是「成立」，不应作为问题上报（也是评审中排除误报的依据）。

✓总线只在值变化时 emit

PluginBus.setData 用 prev !== value 去重，on() 返回可用的 off；setupForceUpdateOnBusKeys 在订阅后主动补一次 forceUpdate，因此「首帧写入派生键」能立刻反映到首屏。回归：test/bus-protocol.test.tsx。

✓首屏变体价已写入派生键

SKUPlugin.onMount 在命中变体后同时写 skuPrice / skuImage（SKUPlugin/create.tsx:92-101），不需要用户先切一次规格；plugins-c.test.tsx 的「选中变体的图优先于 data.image」正是靠这一点。

✓价格重算与事件发布一致

PriceCalculator.onMount 订阅 skuPrice / quantity / couponApplied，recalc 内 emit("price:change") + forceUpdate（PriceCalculatorPlugin/create.tsx:66-98），单价/小计/合计口径在同一处计算，测试有端到端用例。

✓插件清理函数被内核回收

onMount 返回值（off1/off2/off3、ResizeObserver、IntersectionObserver）由内核 PluginManager.clear() 逆序执行；InventoryPlugin:44-45、QuantityPlugin:170-181、CouponRecommendPlugin:56-70 都正确返回 cleanup。

✓插槽故障隔离

composeSlots 与包内 renderDomainSlot 都逐插件 try/catch + PluginErrorBoundary（plugins/slots.tsx:65-84），一个插件 render 抛错只丢自己那段，不会白屏。

✓可见性与尺寸契约

CardCore 只建一次 IntersectionObserver、卸载 disconnect（CardCore.tsx:188-207）；useImperativeHandle 暴露 getContainer/forceUpdate/getSize（:222-233），core-ref.test.tsx 覆盖。

✓两套排序规则一致

内核 composeSlots 与包内 renderDomainSlot 都是「config.order 升序 → priority 降序」，ActionsPlugin 用 order=20 把按钮结构性排在最后（ActionsPlugin:113-115），测试断言价格区顺序。

✓复合组件的「变体精确匹配」本身是对的

product.ts:96-116 用属性集大小相等 + 逐项相等做完全匹配，注释明确解释了「只选一部分时回退商品级价格，而不是拿错价」。这条没错——错的是插件侧用了另一套语义（P1-2）。

P0-1 · 缺省库存被当成 0：未传 inventory 的商品卡首帧「已售罄」，并且整卡点击被蒙层吞掉

P0

function resolveInventory(context): number {
  const variant = context.bus?.getData?.(BusKeys.skuVariant);
  if (typeof variant?.stock === "number") return variant.stock;
  const inventory = (context.data as any)?.inventory;
  return typeof inventory === "number" ? inventory : 0;   // ← 没字段 = 0 = 售罄
}
证据 2
同文件 :47-68 —— soldOut = showOverlayWhenSoldOut && inventory <= 0，覆盖层 position:absolute; inset:0; zIndex:9，没有 pointer-events:none。

...
<div style={{ position:"absolute", inset:0, background:"rgba(0,0,0,0.5)",

证据 3
packages/vane-card/src/components/CardPlugin/types/product.ts:25-26, 44-45 —— 公开类型明确是可选的，并写明语义：stock「缺失表示未知」、inventory?「总体库存（无变体时用）」。
证据 4
packages/vane-card/src/components/CardPlugin/core/CardCore.tsx:248 容器是 position:relative，overlay 段在 children 之后渲染，故蒙层在命中测试最上层、覆盖整卡（含规格按钮与加购按钮）。
后果
任何只传 price / title / image（或不含库存字段）的商品卡，首帧即被半透明黑蒙层覆盖并显示「已售罄」；用户点规格、点加购、点图片全部无效。同时 lowStock 分支（:50）永远走不到。187 个用例全绿是因为 test/plugins-c.test.tsx:124-157 只覆盖了 inventory:50 / 3 与「变体 stock=0」三种有数据场景，没有「字段缺失」用例。
建议
把 resolveInventory 返回类型改为 number | undefined：变体 stock 有值 → 用它；data.inventory 有值 → 用它；都没有 → 不判售罄也不判紧张，直接 return null。蒙层加 pointer-events:none（只保留视觉），售罄状态应通过 ActionsPlugin / 数量步进器禁用按钮表达。补单测：{ title, price } 无库存字段 → 不出现「已售罄」。

P1 问题（真实接入必踩 / 核心交互失效）

这 5 条都发生在「选了规格，价格/库存/主图却没跟着变」这个核心承诺上，或让插件配置在运行时静默失效。

P1-1 · ProductCard 只按插件名记忆 Core：同名插件换配置永不生效

P1
证据 1
packages/vane-card/src/components/CardPlugin/compound/ProductCard.tsx:69-77
const pluginKey = plugins?.map((p) => p.name).join("|") ?? "";
const Core = useMemo(() => {
  if (!pluginKey) return CardCore;
  return withPlugins(CardCore, { plugins: plugins ?? [] });
}, [pluginKey]);   // ← 只依赖名字，同名即不重建
证据 2
packages/vane-card/src/components/CardPlugin/plugins/withPlugins.tsx:66-69 —— 闭包在 HOC 工厂里就把 plugins 固定下来了（const { plugins } = normalized），之后 props 里的新数组不会被读到。
证据 3
packages/vane-card/test/compound.test.tsx:222-224 —— 现有用例「内联 plugins 数组不会导致卡片重挂」正好把这一行为固化成了契约。
后果
最典型的写法 plugins={[createSKUPlugin({ attributes, variants: data.variants })]}（配置由异步到达的 data 派生）在首帧把 variants/attributes 定成 []；数据到达后 pluginKey 不变 → Core 不重建 → 规格选择器永远空白。同理：改券列表、改库存阈值、改 renderIn 都静默不生效，表现为「控件点了没反应」。
建议
把记忆键从「名字签名」升级为「名字 + 配置指纹」（例如 JSON.stringify(p.config) 的稳定哈希，或由调用方显式传 configVersion）；若要保留「不重挂」的收益，可在 HOC 内部用 useRef 保存最后一次 plugins，在引用变化时通过 runtime 的热替换接口更新配置而不卸载树。至少补一条「同名插件换 config 后变体可选中」的测试。

P1-2 · 两套 matchVariant 语义相反：插件侧部分匹配，复合组件侧完全匹配

P1
证据 1
packages/vane-card/src/custom-plugins/SKUPlugin/create.tsx:27-32 —— 只要「已选的每个属性」都能在变体上找到就命中（允许变体多属性）。

// selection = { 颜色:"红" }，变体 attrs = { 颜色:"红", 尺码:"S" } → 命中
证据 2
packages/vane-card/src/components/CardPlugin/types/product.ts:95-116 —— 复合组件要求属性集大小相等，注释还专门解释了为什么必须完全匹配。

双属性商品（颜色 + 尺码）下，用户只选了颜色，插件就命中数组里第一条该颜色变体并把它的 price / stock / image 写进总线；再选尺码时 find 仍返回同一条 → 价格完全不随第二个属性变化。同时复合组件 Price（Price.tsx:17-18）走完全匹配，两个体系会显示两个不同价格。数组顺序不同还会出现「每次刷新价格不一样」。

P1
证据 1
packages/vane-card/src/custom-plugins/SKUPlugin/create.tsx:113-133 —— footer 分支只在 matched 存在且 price 是数字时才写；不匹配时什么都不做，skuPrice/skuImage/skuVariant 保持上一次的值。

证据 2

证据 3

后果
① 用户从「红/有货」切到「绿/缺货」：matchVariant 未命中（或命中无 stock 的新变体）→ skuVariant 仍是红 → 库存覆盖层不出现，用户以为有货；② PriceCalculator（:69-70）读到的 skuPrice 还是红的价，与选中的绿不符；③ 只装 SKUPlugin（不装 PriceCalculator）时，选择器点击后没有任何订阅者 forceUpdate → 选中态高亮都不刷新。测试 bus-protocol 覆盖了「键冻结 / 变体价写入」，但没有「从不匹配回到匹配 / 从有价到无价」的清写场景。

P2 问题（契约 / 成本 / 生命周期，可排期）

单独看不致命，但会抬高接入成本：插件作者按类型写代码不生效、渲染期副作用在并发下不安全、异常后槽位再也回不来。

P2-1 · transformData 钩子有声明、无执行：卡片数据流水线是空的

P2
证据
packages/vane-card/src/components/CardPlugin/plugins/types.ts:143 声明 transformData?: (context, data: T) => T；全包 grep transformData 只有 2 处命中（types.ts:119 注释 + :143 声明），withPlugins.tsx 与 usePluginRuntime 里都没有调用点。

P2

同一帧内连点两次，两次都算出 true 并 emit 两次「已加入」，但用户预期是「加入 → 移出」。与 rerender-functional-setstate 规则冲突；购物车这种幂等敏感操作会被下游计数错。
建议
改用函数式 setState(prev => { const next = !prev.cart; ... return { cart: next } })，emit 放到 effect 或 updater 返回后再发（updater 保持纯函数的既有约定）。

P2-6 · GalleryPlugin：index 越界崩溃、渲染期写总线、window.open 未校验 scheme

P2
证据 1
packages/vane-card/src/custom-plugins/GalleryPlugin/create.tsx:44, 54, 58 —— const current = slides[index] 后直接 current.type，index 只在用户操作时取模，不随 slides 变短钳制。

证据 2

证据 3
同文件 :65 window.open(current.src, "_blank")，current.src 来自 data.images / 配置，未做 scheme 白名单；:68 加载失败硬编码回填 /404.jpg（相对路径可能 404）。

P2-7 · ImagePlugin 换图后状态不复位：图裂过一次，换新图仍显示图裂

P2
证据
packages/vane-card/src/custom-plugins/ImagePlugin/create.tsx:41-48 的 useState<"loading"|"loaded"|"failed">("loading") 没有随 src 重置的 effect；:50-68 的 failed 分支直接 return 掉整个 img，不再有机会加载新图。
后果

P2-8 · QuantityPlugin 输入防抖定时器卸载不清理

P2
证据
packages/vane-card/src/custom-plugins/QuantityPlugin/create.tsx:49, 104-116 —— timerRef 只在新输入时 clearTimeout，没有卸载清理 effect。
timerRef.current = window.setTimeout(() => {
  const n = Number(val);
  if (Number.isFinite(n)) setQ(n);   // 卸载后仍会写 bus.setData(quantity)
}, 150);
后果
卡片在输入后 150ms 内卸载（列表滚动复用时常见），定时器仍会执行 setQ → 往已卸载实例的 bus 写数据；如果跨实例共享 bus（自定义实现），会把旧卡的数量写到新卡。
建议

安全审查（security-best-practices）

结论：没有可利用的注入面。所有商品字段都由 React JSX 渲染或进入样式属性，不存在字符串拼 HTML；风险集中在「外部跳转」与「第三方插件输出」两个边界。

注入与凭证

XSS安全全包无 dangerouslySetInnerHTML / new Function / eval；data.title、sku.sku、coupon.code 全部走 JSX 文本节点（React 自动转义）。
唯一 innerHTML安全A11yToolbar.tsx:20 的 style.innerHTML 注入的是模块级静态常量 CSS，不含任何外部输入。
图片地址注意<img src> 接受任意字符串：javascript: 在 img 上不会执行，但 data:/blob: 会绕过内容策略；建议在接入层做域名白名单。
凭证安全包内无 token / cookie / localStorage 读写；Analytics 只上报事件，不读浏览器凭据。

外部跳转与插件面

window.open低危GalleryPlugin/create.tsx:65 与 ReturnPolicy.tsx:84 直接 window.open(url, "_blank")，未校验 scheme。若 images/video/policyLink 来自后台富文本，javascript: URL 可在点击时执行（新窗口 opener 场景）。
第三方插件注意插件的 renderXxx 返回 ReactNode，即使第三方插件返回 HTML 字符串也会被转义；但 onMount 拿到 getContainer() 后可任意 DOM 操作——这是能力而非漏洞，接入第三方插件时需信任边界。
数据外发注意AnalyticsPlugin 上报 cardId、点击坐标、停留时长；属行为数据，需在隐私政策中说明并支持关闭。
建议抽 openExternal(url)：仅 http/https 通过，其余 console.warn 并忽略；同时给 <img> 加 CSP 约束。
