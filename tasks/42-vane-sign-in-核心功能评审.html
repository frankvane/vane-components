01

核心数据流与职责边界

签到的「真相」全部放在消费方的 props.data 里：今天签没签、连签几天、日历每格什么状态、还有几次补签，都是服务端算好后发下来的字段。包内没有第二个真相源，也没有任何日期运算。这条边界决定了后面所有结论的性质——不是「算错了」，而是「没人算」。

① props.data

todaySigned / streak / calendar / makeup / rewards / nextResetAt / history 由宿主填，包里无 schema 校验、无默认值兜底。

② 五段领域槽

Core 固定五段：renderHeader / renderCalendar / renderRewards / renderActions / renderFooter，每段按插件排序后逐个调用。

③ 插件纯渲染

17 个插件只读 ctx.data 做展示；有内部态的只有 Remind / RuleExpand / TodayCheckIn（后者无态）。

④ 回调下发

sign / claim / makeup / share / remind / invite 交给宿主；类型允许返回 Promise，但返回值全被丢弃。

⑤ 宿主回写

请求成功后宿主重新拉 data 触发重渲染。无 pending、无 error、无乐观层、无重试。

02

已验证成立的核心机制

这几条在上一轮出现过问题或在同类包里容易写错，逐条核对后确认「当前实现是对的」，不应作为缺陷上报。

✓五段槽不重影

HOC 刻意不用内核 composeSlots，children 只兜 renderOverlay（withPlugins.tsx:104-120，注释 :105-110 写明了双渲染事故）。test/slot-dup.test.tsx 断言「天连签 / 黄金会员 / 领取记录 / 活动规则」各只出现一次。

✓单插件抛错不连坐

renderSignInSlot 先 try/catch 包住 hook 调用（slots.tsx:57-76），再套 PluginErrorBoundary（:66）；坏插件只丢自己那一段，其余四段照常。

✓禁用态确实由数据驱动

签到按钮 disabled={todaySigned} 且 data-signed 同步（TodayCheckInPlugin:38-41）；奖励 claimed 走终态文案（RewardPreviewPlugin:71-75）；补签按 available - used 置灰（MakeupSlotPlugin:36）。

✓日历格 key 用日期而非下标

CalendarStripPlugin:64 与 CalendarGridPlugin:45 都用 key={c.date}；补签/重取数据后不会错配内部状态。

✓空集合一律优雅降级

calendar ?? []（Strip:50 / Grid:32）、rewards ?? []（Preview:33 / Milestone:29）、history ?? []（History:31）、rules 为空直接 null（RuleExpand:18），都返回 null 而非空容器。

✓槽内排序确定

config.order 升序 → priority 降序（slots.tsx:51-55），与内核一致；header 里 Streak(10) → Countdown(14) 的顺序稳定。

✓根容器背景与字色成对

SignInCore.tsx:67-71 同时写 background:"#fff" / color:"#1f2328"，深色宿主里不会出现低对比度文字（ADR-13）。

✓无监听器与定时器泄漏

全包 src 检索 setInterval / setTimeout / addEventListener 0 命中；useEffect 只用于 onMount / onPropsChange，依赖为稳定的 execute，重复执行风险已规避。

03

P0 问题（并发签到）

端到端确认结论：存在「点击两次并发签到」，且同样的空窗在「领奖」上重复出现。判定为 P0 的前提是服务端未做幂等——而客户端这边确实没有为它兜底的任何机制。

P0-1 · 签到 / 领奖按钮没有在途锁：请求飞行期间可无限次点击

P0
证据 1
packages/vane-sign-in/src/custom-plugins/TodayCheckInPlugin/create.tsx:36-53
const { todaySigned } = ctx.data;
<button type="button" data-testid="si-checkin-btn"
  data-signed={String(todaySigned)}
  disabled={todaySigned}                                  // 唯一的锁：服务端真相
  onClick={() => !todaySigned && ctx.callbacks.sign?.()} // 不 await、不置 pending
>
证据 2
plugins/types.ts:87 的类型明确允许异步：sign?: () => void | Promise<void>;；但返回值在 TodayCheckInPlugin:41 被直接丢弃。
证据 3
types.ts:70-83 的 SignInData 没有 signing / pending / error 字段；RewardClaimPlugin:41-46 的领取按钮同样无在途态：onClick={() => ctx.callbacks.claim?.(target.day)}。
后果
todaySigned 只有等宿主重新拉取数据后才变 true——在网络往返（200ms～2s）内按钮始终可用。移动端双击、或用户觉得「没反应」连点三次，就会发出 2～3 个签到请求，领奖同理。若后端不是幂等实现，直接产生重复签到 / 重复发积分与券，也就是「签到数据错乱」。即使后端幂等，也会出现第二条请求报错、用户看到错误提示的次生体验问题。
另证
客户端禁用态不是安全边界：disabled 只影响这个按钮，任何脚本仍可直接调用 callbacks.sign()。服务端必须自行按 (userId, 服务器业务日) 幂等，但包文档（README.md:16）把「数据驱动禁用态」写成了防重手段，容易让接入方误以为安全。
建议
插件内维护 const [pending, setPending] = useState(false)，点击后立即 setPending(true) 并 await ctx.callbacks.sign?.()，finally 里复位；按钮 disabled={todaySigned || pending} 并显示 loading 文案。若要跨插件共享，应在 SignInData 增加 signing（由宿主回写）并让 CTA 读它。补一条「连点两次只调用一次 sign」的单测（可用 vi.fn() 返回未决 Promise）。
04

P1 问题（真实接入必然踩到）

四条里两条是「日期与时区契约空洞」，一条是「失败不可见」，一条是「补签选错日期」。它们都不是边角场景，而是签到这个功能的定义域。

P1-1 · 失败没有提示、没有回滚通道；提醒开关本地乐观态永不回退

P1
证据 1
plugins/types.ts:86-93：SignInCallbacks 六个回调全部返回 void | Promise<void>，不接收也不回传错误；SignInData（:70-83）也没有 error / message / status 字段。
证据 2
src/custom-plugins/RemindPlugin/create.tsx:20-25
onClick={() => {
  const v = !on;
  setOn(v);                       // 先乐观切换
  ctx.callbacks.remind?.(v);      // 返回值丢弃，失败也不回退
}}
后果
签到失败（网络断、风控拦截、当日已签）时，UI 上没有任何反馈：按钮仍是「立即签到」，用户重复点击（进一步放大 P0-1）。提醒开关在持久化失败时永久显示「已开启提醒」——这正是「失败后 UI 停留在成功态」的同构问题（对签到 CTA 来说，因为不写乐观态反而不会卡在「今日已签」，但代价是完全静默）。
建议
回调签名改为 (...args) => Promise<void> 并在包内 try/catch；SignInData 增加 lastError?: { code, message }，或给 CTA 加 errorText 插槽；Remind 改为受控（读 data.remindEnabled）或失败时回退 setOn(!v)。补「remind reject 后开关回到原态」单测。

P1-2 · 日期与时区契约是空的：没有工具函数、没有时区约定，展示层还会差一天

P1
证据 1
plugins/types.ts:36-37 只写 date: string; /** ISO yyyy-mm-dd */——没有说明这是服务器时区日、本地时区日还是 UTC 日；:79 的 nextResetAt?: number 也没有任何时区/口径注释。
证据 2
src/custom-plugins/CountdownPlugin/create.tsx:30 const diff = nextResetAt - Date.now();；一旦宿主按「本地 23:59」构造（new Date().setHours(23,59,59)），就与服务器按 UTC 日切线的判定相差 8 小时（东八区）。
证据 3
src/custom-plugins/RewardHistoryPlugin/create.tsx:53
{new Date(h.at).toLocaleDateString()}
证据 4
packages/vane-sign-in/demo/src/demos/lib/sampleData.ts:10-25：整个演示的日历是硬编码 date: `2026-10-${String(day).padStart(2,"0")}`，"today" 恒为第 8 天，与真实日期（2026-11-01）无关——说明包内确实没有日历生成器，连示例都绕过了日期计算。
后果
跨月（31 天）、闰年（2/29）、DST（欧美/南半球时区）以及「当天边界」这四类日期计算，全部由接入方自行实现且没有任何约定。最典型的线上事故是：服务器按 UTC 日期判定「今天」，中国用户 00:00–08:00 签到会被记到昨天，或日历里「今天」高亮落在昨天那格——差一天。而 toLocaleDateString() 在 SSR（Node 服务器时区）与浏览器（用户时区）会输出不同结果，同时造成 hydration mismatch 与领取记录日期错位（UTC-5 用户看到的 Date.UTC(y,m,d) 会回退一天）。
建议
导出三件事并写进类型注释：① toDayKey(date, tz)（固定用 Intl.DateTimeFormat("en-CA",{timeZone}) 取 yyyy-mm-dd）；② diffDays(a,b)（按 DayKey 计算，不碰 Date 相减，天然免疫 DST）；③ 明确 nextResetAt 用绝对 epoch ms、date 用「业务所在时区」的 DayKey。展示层用 formatDayKey(h.at, tz) 而不是 toLocaleDateString()。

P1-3 · 跨天边界不闭环：倒计时不 tick，跨夜按钮不复位

P1
证据 1
src/custom-plugins/CountdownPlugin/create.tsx:13-15 注释自述「纯渲染计算（无定时器），由消费方在 nextResetAt 变化时重渲即可刷新」；:30-44 只在渲染时读 Date.now()。
证据 2
src/custom-plugins/TodayCheckInPlugin/create.tsx:40-41：按钮可用性只看 ctx.data.todaySigned，包内没有任何「到 nextResetAt 自动置 false」的逻辑（src 无 setTimeout/setInterval，检索 0 命中）。
后果
用户 23:50 打开页面放着不动，00:10 点「立即签到」：如果 todaySigned 已是昨天签到的 true（宿主通常缓存到刷新为止），按钮仍是灰的「今日已签 ✓」，用户会以为自己断签了；倒计时文案「距下次可签到 5小时30分」也不会递减，永远是渲染那一刻的旧值。反过来，倒计时到 0 之后不会自动变成「现在可签到」，除非宿主撞上一次重渲染。
建议
在 Core（而不是插件）里起一个 1s 定时器只更新 now，通过 context 下发：Countdown 与 TodayCheckIn 用 now >= nextResetAt 参与判定；同时监听 visibilitychange 与 focus，回到前台时触发一次宿主 refresh()（可通过 callbacks.refresh 新增）。补「跨过 nextResetAt 后按钮变可用」的假时钟单测（vi.setSystemTime）。

P1-4 · 补签目标按数组顺序取第一个，且完全不校验补签窗口

P1
证据
src/custom-plugins/MakeupSlotPlugin/create.tsx:34
const target = (calendar ?? []).find((c) => c.canMakeup);   // 无排序、无日期比较
...
onClick={() => target && ctx.callbacks.makeup?.(target.date)}  // 只传 date
补充
DayCell.canMakeup 的类型注释是「漏签且仍在补签窗口内」（types.ts:41-42），判定责任被完全外移；包内没有「date <= today」「窗口天数」「每轮仅一次」任一校验。
后果
服务端返回的 calendar 若是「本月 1 号起」或按 date 倒序/乱序，补签按钮补的可能是 1 号（最老的）也可能是最近一天，取决于数组顺序——运营规则无法保证。更危险的是未来日期：若后端误把明天格标了 canMakeup，前端会照补，产生「补签未来」这类数据错乱。另外 makeup.available - used 只是展示配额，不参与目标选择。
建议
改为按业务规则显式选目标：calendar.filter(c => c.canMakeup && c.date <= todayKey).sort(by date)[0]（或让 SignInData 直接下发 makeupTarget?: DayCell，把规则收回服务端）；补签回调改为 makeup(date, { dayIndex }) 便于对账。补「数组倒序时仍补最早漏签日」单测。
05

P2 问题（契约 / 成本 / 可维护性）

这些不会立刻破坏业务，但会让「接进去才发现不对」和「改一个小地方要动三处」的概率显著上升。

P2-1 · 领域槽 key 带 index，插件顺序变化丢开关状态

P2
证据
src/components/SignInPlugin/plugins/slots.tsx:66：key={`signin-slot-${plugin.name}-${index}`}。
后果
调整 order/priority 或增删同槽插件 → index 位移 → RemindButton（RemindPlugin:16-38）的开关态与 RuleBlock（RuleExpandPlugin:16-34）的展开态被重挂载重置。
建议
key 只用 plugin.name。

P2-2 · Provider 的 useMemo 无效；每次渲染做 5 次排序

P2
证据
slots.tsx:33-37 依赖 [orderedPlugins, context]；plugin-core/src/react/usePluginRuntime.ts:157 的 context 依赖 props 与 extendContext，后者又是 useCallback(..., [props])（withPlugins.tsx:43-53）。
后果
宿主任意一次 setState（输入框、滚动驱动）都会让 context 换身份 → Provider value 变化 → Core 的 5 个 useSignInSlot 全部重跑（SignInCore.tsx:36-40），每个槽都重新 filter/sort/map（slots.tsx:45-56）。插件数 P 时每渲染 ≈ 5 × O(P log P) + 5 × P。
建议
HOC 里按槽预分组并 memo；extendContext 依赖收敛到具体字段，避免整包 props 换身份。

P2-3 · 渲染期写 ref：ctxRef.current 在函数体内赋值

P2
证据
withPlugins.tsx:64-67：ctxRef.current = runtime.context 写在 render 阶段（Profile 包同样问题）。
后果
React 18 可用但违反 rerender-use-ref-transient-values 前提；未来并发渲染下插件执行（execute → manager.executeHook(contextRef.current!)）可能拿到未提交的 context。
建议

P2-4 · transformData 钩子在本包永不执行

P2
证据
withPlugins.tsx:76 只调 runtime.transformProps(props)；src 内检索 transformData 仅命中类型注释（plugins/types.ts:143-144 继承自内核）。

P2-5 · 声明了却从未使用的配置项（defaultOn / defaultOpen）

P2-6 · 补签文案与状态不符：无目标但仍有配额时仍显示「次数已用完」

P2

P2-7 · 日历色板有两份且已经漂移

P2

CalendarStripPlugin/create.tsx:17-23 自带一份 COLORS，而 tokens.ts:18-27 又有一份 DAY_COLORS；同一个 signed 态前景色是 #c2410c vs #d35400，missed 是 #6b6b6b vs #7d7d7d。CalendarGrid 用 tokens，CalendarStrip 用自己的。

P2-8 · 缺字段防御不一致：补签整段会静默消失、连签会显示 undefined

P2

MakeupSlotPlugin:33-36 直接解构并访问 makeup.available（无 ?? 兜底），而其它插件普遍 calendar ?? [] / rewards ?? []。

P2-9 · 展示格式与可访问性细节

P2
证据 1
RewardPreviewPlugin:33-49：filter(...) 后直接 slice(0, limit)，未按 day 排序——服务端乱序时预告顺序也乱。

后果
奖励预告可能把「第 30 天大奖」排到列表末尾而看不到；倒计时在长周期场景不可读；键盘/读屏用户拿不到日历状态。
建议

06

安全审查（security-best-practices）

结论：注入类风险为零（无危险 DOM、无 URL 输出、无凭证读写）；真正要写进接入文档的是「客户端禁用态不构成安全边界」。

注入与凭证

XSS安全src 检索 dangerouslySetInnerHTML / innerHTML / eval / new Function 0 命中；所有 rules / label / liveTitle 类文本都进 React 文本节点，自动转义。
URL 输出安全本包不拼任何 href/src/CSS url()；分享/邀请只回调宿主，二维码不在此包（对比 vane-profile 的 P1-4）。
凭证 / 隐私安全无 localStorage / sessionStorage / document.cookie / fetch / token（检索 0 命中）；包内不持有登录态，也不打印用户数据（仅 console.warn 插件名）。
外链属性安全无外链渲染，因此无 target/rel 缺口。

业务安全边界

防重放P0客户端没有在途锁与幂等键（P0-1）。服务端必须按 (userId, businessDay) 唯一约束；README.md:16 把「禁用态」当作防重手段，属于误导性文档。
信任边界P1todaySigned / canMakeup / reward.claimed 全部由 props 决定，组件不校验也不签名；任何可写 props 的代码都能让 UI 显示「已领」。这是设计取舍，需在文档里明确「展示层不负责校验」。
补签P1回调只传 date（MakeupSlot:46），服务端必须自行复核窗口与配额，否则前端可选任意 canMakeup=true 的格子。
供应链安全零运行时依赖（peer 仅 react / vane-plugin-core），发布仅 dist，无新增供应链面。
07

React / 性能审查（vercel-react-best-practices）

按「避免无谓渲染 / 热路径分配 / effect 与渲染纯函数」三条线核对。好消息：没有监听器与定时器泄漏；坏消息：Date.now() 进了渲染函数，SSR 与客户端输出必然不一致。

成立的部分

异常隔离正确渲染期 try/catch + 每插件 PluginErrorBoundary（slots.tsx:57-76）双保险，符合「单点故障不扩散」。
列表 key正确日历格以 date 为 key（Strip:64 / Grid:45），嵌套 map 的二维码式点阵也用行列坐标复合 key。
内部态归属正确RemindButton / RuleBlock 都拆成独立组件，hooks 发生在 React 上下文内，没有「插件函数里调 useState」的规则破坏。
订阅粒度正确插件只从 context 读自己需要的字段；算 & 渲染在同一个组件内，没有额外的 effect 中间态（rerender-derived-state-no-effect 达标）。

缺口

渲染非纯CountdownPlugin:30 在 render 内调 Date.now()；测试里 renderToStaticMarkup 走的是服务端渲染路径，服务端时间与客户端时间不同 → diff 不同 → 文案不同 → hydration mismatch（且倒计时本来就不 tick，见 P1-3）。
memo 失效SlotProvider value 随 props 身份变化重建（P2-2），宿主任意 setState 都会让 5 个槽重跑；SignInCore.tsx:36-40 每次渲染调 5 次 useSignInSlot，无缓存。
热路径分配5 次 [...plugins].filter().sort().map() 每渲染重建（slots.tsx:45-56）；CalendarStrip / CalendarGrid 每次重建全部格子样式对象（内联 style 对象无 memo）。
渲染期写 refwithPlugins.tsx:64-67（P2-3）；同时在 render 内执行 runtime.transformProps(props)（:76），属于「渲染期跑插件链」，插件若有副作用会按渲染次数重复。
SSR 可用性除 Countdown 外无其它时间/随机源；useImperativeHandle（SignInCore.tsx:42-55）只暴露容器能力，不影响 SSR。
