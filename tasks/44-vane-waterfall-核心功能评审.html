01

核心数据流与职责边界

理解问题的坐标：瀑布流的「数据面」与「布局面」在 HOC 层被拆开。数据插件改的是 transformProps().items，而插件上下文里的 items 是另一份状态 —— P1-3 与 P2-1 都源自这条边界。容器必须由调用方给出确定高度，否则没有滚动上下文（packages/vane-waterfall/README.md:54），虚拟化与触底都不会成立。

① 装配与数据面

消费方 props 进入 transformProps 链；Filter / Sort / Search / Pagination / FixedHeight 会产出新 items 数组。

② 测量

项挂载后读 el.offsetHeight 写入 measuredHeightsRef；项级 ResizeObserver 监听后续高度变化。

③ computeLayout

纯函数按 shortest / balanced / sequential 选列，列高只认最终 position，产出位置 Map 与 totalHeight。

④ 虚拟化

computeVisibleRange 只决定渲染窗口；未渲染项按实测样本中位数估值占位，容器高度始终取全量 totalHeight。

⑤ 滚动与钩子

handleScroll 更新视口、触底判定、进入/离开事件；HOC 再把 20 个领域钩子分发给插件。

02

已验证成立的核心机制

这些是瀑布流最容易写错、也最容易被误报的地方。逐条按源码与单测核对后判定「成立」，不应作为问题上报。

✓布局是纯函数，列分配与旧算法等价

layout.ts:91-220 不碰 DOM；test/core-layout.test.ts:17-37 用 8 组数字快照锁住 shortest / balanced / sequential 的列分配与比较顺序，避免重构悄悄改版式。

✓列高推进只认最终 position

layout.ts:202-208 用 position.y + position.height + rowGap 推进目标列，而不是用插件返回值；插件改 column 时 x 由本轮列宽统一补齐（:192-196），PinItem 不会因 gap 来源不同而错位。

✓「量到就重排」链路是真的

项 RO 回调只在「当前 position 高度与实测差 > 0.5 且该高度未补过」时 scheduleLayoutNow()（WaterfallCore.tsx:695-705），并用 rAF 合并（:488-494）；heightRepairRef 防止同一高度反复触发，实测不会自激震荡。

✓并发布局请求不会丢失参数变更

WaterfallCore.tsx:349-355 用布局参数签名判重，期间到达且参数不同的请求置 pendingRelayoutRef，结束前用最新闭包补跑（:444-449）；core-props.test.tsx:169 覆盖「布局期间到达的请求不会被丢弃」。

✓虚拟化只裁渲染，不缩总高

内容层高度直接取 layoutInfo.totalHeight（WaterfallCore.tsx:876-883），卸载离屏项不会让滚动条变短；估值取实测样本中位数并带 8px 滞回（virtualize.ts:57-72 + WaterfallCore.tsx:386-400）。

✓容器 / 项 observer 与定时器都清理

卸载时 containerObserver.disconnect()、逐项 observer disconnect、清 scroll-end 与布局定时器、cancelAnimationFrame（WaterfallCore.tsx:612-632）；core-resize.test.tsx:155 断言 observer target 清空。

✓列数 / 间距变化立即重排，items 变化走防抖

布局参数 effect 直接 void calculateLayout()（:656-671），items effect 走 throttledCalculateLayout()（:646-652）；长生命周期回调统一走 calculateLayoutRef（:466-470），不存在「拖列数又弹回旧值」的陈旧闭包。

✓DOM 顺序 = 数据顺序，绝对定位只改视觉

渲染按索引升序输出（:884-917），定位用 transform / left-top，不重排 DOM；key 来自 keyExtractor（默认 index）。因此屏幕阅读器的阅读顺序是数据时间顺序，而不是视觉列顺序 —— 对信息流是合理的。

P1 问题（建议本迭代修）

以下 6 条都会在真实接入（图片信息流 / 筛选排序 / 大列表虚拟化 / 无限滚动）中被触发，且每条都有代码证据。

P1-1 · 消费方回调抛错一次，布局标志永不复位，整个瀑布流冻结

P1
证据 1
packages/vane-waterfall/src/components/WaterfallPlugin/WaterfallCore.tsx:357-366：isCalculatingLayoutRef 置真后 await onBeforeLayout?.()，抛错时没有 try/finally；只有回调返回 false 才会复位。
isCalculatingLayoutRef.current = true;            // :357
...
const beforeResult = await onBeforeLayout?.();     // :362  抛错 → 直接跳出
if (beforeResult === false) {
  isCalculatingLayoutRef.current = false;          // 只有这条分支复位
  return;
}
证据 2
同文件 :369 / :441-442：onLayout?.() 与 onLayoutComplete?.() 也在这段临界区内，抛错同样让 :442 的复位被跳过。
onLayout?.();                                     // :369
...
onLayoutComplete?.();                             // :441  抛错
isCalculatingLayoutRef.current = false;           // :442  被跳过
触发面
这三个回调由 HOC 原样转发给消费方（withPlugins.tsx:424-436）。插件钩子本身已被内核逐插件 try/catch 隔离，但消费方回调没有隔离：埋点上报、Promise 校验、业务校验任何一处 throw 都会触发。另 onScroll 在 WaterfallCore.tsx:535 无条件调用，抛错会跳过其后的触底判定与进入/离开事件。
后果
标志一旦卡在 true，后续所有 calculateLayout 都在 :350-355 早退（签名相同则连 pendingRelayout 都不置），项挂载后的补排（:699-705）、items 变化、列数变化全部失效：瀑布流永久停在旧布局，新数据不再定位、不再显示，只能卸载重挂载恢复。
建议
把 calculateLayout 主体包进 try/finally，finally 里复位标志并处理 pending；消费方回调统一走 safeInvoke（catch + console.warn）。补一条「onLayoutComplete 抛错后下一次布局仍正常」的回归单测。

P1-2 · 数据集替换后测量缓存按索引复用，虚拟化下离屏项沿用旧高度

P1
证据 1
WaterfallCore.tsx:272-273 声明 measuredHeightsRef「项被虚拟化卸载后仍然记得」，按 index 为键。
/** 已测到的真实高度：项被虚拟化卸载后仍然记得 */
const measuredHeightsRef = useRef<Map<number, number>>(new Map());
证据 2
同文件 :646-652：items 变化时只清 heightRepairRef，没有清 measuredHeightsRef；下一次布局在 :372-380 用索引回退旧值。
useEffect(() => {
  hasInitialLayoutRef.current = false;
  hasRequestedLayoutRef.current = false;
  heightRepairRef.current.clear();   // 只清“某高度已补过一次”的记录
  throttledCalculateLayout();        // measuredHeightsRef 没有清

触发面
Filter / Sort / Search / Pagination 都是官方插件，都会让同一个 index 在替换后指向不同项；非虚拟化时所有项都挂载、offsetHeight 即时实测，问题被掩盖；一旦开启 virtualize（官方场景就是千项列表），离屏项没有 DOM，只能命中旧缓存。
后果
位置与总高按错误高度计算：短项占用长项的高度 → 列尾空白/滚动条虚长；长项占用短项高度 → 卡片重叠。滚动到这些项时每挂载一个就触发一次 scheduleLayoutNow（:702-704），布局与滚动位置连续抖动，直到整段被重新测量才收敛。
建议
缓存键改为稳定身份（keyExtractor(item) 的结果）并随数据集一起换 Map；或至少在 items 身份变化时 measuredHeightsRef.current.clear() 并重置 estimateRef。补「同长度、仅重排的数据集替换后离屏位置全部重算」单测。

P1-3 · 数据插件每次渲染都产出新 items 数组，滚动时被当成「数据集变化」反复全量重排

P1
证据 1
withPlugins.tsx:357-358 在每次 HOC 渲染都跑完整 transformProps 链；Filter / Sort / Search / Pagination / FixedHeight 都返回新数组：
// FilterPlugin/create.ts:26-33

// PaginationPlugin/create.ts:29-30

证据 2
withPlugins.tsx:454-460：滚动时 onScroll 立刻 syncFromCore()，HOC 因 setViewport 重渲染；而 WaterfallCore.tsx:646-652 只按 items 引用判断数据集变化。
useEffect(() => {
  ...
  throttledCalculateLayout();          // 新数组 → 每次都当新数据集
}, [items, throttledCalculateLayout]);
后果
滚动期间每个滚动事件都会：Core setViewportInfo 一次 + HOC syncFromCore 一次（两处 setState）→ HOC 重跑整条插件链（O(插件数 × N)）→ 产出新 items → Core 每 150ms（默认 debounceDelay）做一次 O(N) 全量 computeLayout + Map 重建 + Core 重渲染。数据一行没变，却持续重排；项数 1000 时滚动掉帧明显，且每次布局都会重写 itemPositions，放大 P2-10 的上下文陈旧问题。
建议
把 transformProps 结果按 props.items 引用 + 插件集合引用做 useMemo；或 Core 用「keyExtractor 首/尾 + 长度」指纹判断数据集是否真的变了。滚动同步用 rAF/节流合并，且只同步 isScrolling 这类必需值。补「滚动 N 次只发生 1 次布局」测试。

P1-4 · 触底判定只存在于 scroll 事件：首屏内容不足一屏时无限滚动永不触发

P1
证据 1
WaterfallCore.tsx:540-543 是全包唯一调用 onReachBottom 的地方，且位于 handleScroll 内。
if (onReachBottom) {
  const distanceToBottom = scrollHeight - (scrollTop + clientHeight);
  if (distanceToBottom < reachBottomOffset) onReachBottom(distanceToBottom);
}
证据 2
InfiniteScrollPlugin/create.ts:40-54 只监听 onReachBottom；布局完成（onLayoutComplete）、容器 resize（handleResize）都没有补检。
触发面
首屏只有 5–10 项、屏幕很高、或过滤后只剩少量内容时，scrollHeight <= clientHeight，容器根本没有可滚动范围 → 不产生 scroll 事件 → onLoadMore 一次都不会调。追加一页后如果用户停留在底部，部分浏览器也不会因内容变高自动派发 scroll。
后果
首屏永远只有一页：空状态无法恢复、窄屏数据量小的信息流「加载更多」按钮不出现；再叠加 withPlugins.tsx:167 的 hasMore 无外部写入路径，消费方既不能自动加载，也不能按文档置 hasMore=false。
建议
把判定抽成 maybeReachBottom()，在 onLayoutComplete、容器 resize、items 变化后各补一次（内容不满一屏时 distance 为负，天然满足）；或改用底部 sentinel + IntersectionObserver。补「3 项内容 + 600px 容器 → onLoadMore 触发一次」单测。

P1-5 · 实测高度回写没有滚动锚定：视口上方的重排会让滚动位置跳

P1
证据
WaterfallCore.tsx:402-429 用新高度重算全部位置后只写 state / ref，从未调整 container.scrollTop。
const result = computeLayout({ heights, columns, ... });
layoutInfoRef.current = nextInfo;
positionsRef.current = result.positions;
setLayoutInfo(nextInfo);               // :428
setItemPositions(result.positions);    // :429  上方项变高，scrollTop 不变 → 内容整体位移
叠加
图片加载完成 / 字体回流 → 项 RO 触发 scheduleLayoutNow（:686-705），同一帧内可能连续补排多次；ScrollAnchorPlugin 只监听 anchor:scrollToId 做跳转（ScrollAnchorPlugin/create.tsx:20-27），并不做锚定补偿。
后果
用户在视口下方阅读时，上方若干项从估值变成真高，y 变大 → 当前可见内容整体向下推，视觉上「页面自己跳了一下」；估值偏低时快速滚动还会出现若干帧卡片重叠。README 也自述拖动滚动条瞬移时峰值约 60px（packages/vane-waterfall/README.md 的「虚拟化的估值策略」一节）。
建议
布局前记录首个可见项及其视口内偏移，布局后读新 position 计算 delta 并同步修正 container.scrollTop（同一布局 effect 内完成，避免可见帧）；或提供 scrollAnchor 开关并在文档说明。补「项 0 从 100 长到 300、滚到项 5 后其屏幕位置不变」单测。

P1-6 · 零高度项被整体跳过：图片失败 / 懒加载未定尺寸时项永久不可见

P1
证据 1
layout.ts:84-89 与 :146-150：实测 0 且无估值时 continue，该项不进入 positions、不占任何高度。

P2-6 · 持久化组：恢复时机过早 / 无 schema；URLSync 只写不读；Bookmark 重复监听

证据 2

P2-7 · Grouping / StickyHeader 名不副实：每次布局 O(n) 重算 + emit，吸顶只显示第一个分组

P2-9 · 无障碍：每一项 tabIndex=0 + outline:none；虚拟化下读数语义不完整

06

安全审查（security-best-practices）

结论：没有可利用的注入面。所有用户内容都经 React / DOM 属性写入，不存在字符串拼 HTML；外部输入（URL、localStorage）只参与数值/字符串比较或分页切片，不进入渲染。

注入与数据边界

XSS sink安全对 src 全量检索 innerHTML | dangerouslySetInnerHTML | new Function | eval( | document.write | insertAdjacentHTML | javascript: → 无命中。
DOM 写入安全插件只写静态属性 / style：A11y 的 setAttribute 值为配置常量，Transition / Recycle 写 style.transition / visibility，DragReorder 用 elementFromPoint + Number() + 固定属性选择器。
React 转义安全renderItem / renderItemWrapper / 覆盖层返回的都是 ReactNode，文本节点自动转义；插件异常由 PluginErrorBoundary 兜住（withPlugins.tsx:411-414）。
URL安全URLSync 用 URLSearchParams.set（自动编码）拼 search/hash，再 history.replaceState；只写不读回渲染，无开放重定向 / 伪协议面。
网络安全包内无 fetch / 远程脚本 / 图片加载；detectNetwork 只读 navigator。

可篡改输入与低危项

localStorage低危StatePersistence / Bookmark 读同源存储后不校验 schema。值只进入 props（分页/查询）或 scrollTo，不构成注入；但非数字 pageSize 会让 Pagination 算出 NaN → 静默空页（见 P2-6）。
URL 参数注意URLSync 把参数只通过 bus.emit("urlsync:init") 广播，页面若自行渲染这些值需按普通不可信输入处理（库本身不渲染）。
配置注入安全插件配置只用于数值计算（阈值、列宽、poolSize）或 React 文本；StickyHeader 的 title 作为文本节点输出，自动转义。
日志安全仅 debug 打尺寸/估值，ClickAnalytics 的 log 只打 index 与总数；无 PII 与凭证。
建议为持久化加版本化 schema + 字段白名单；对 pageSize / pageIndex 做 Number.isFinite 校验；其余不建议引入额外安全机制。

React / 性能审查（vercel-react-best-practices）

按「避免无谓渲染 / 热路径分配 / effect 生命周期 / 渲染期副作用」四条主线核对。

成立的部分

rAF 合并正确scheduleLayoutNow 用一个 rAF 句柄合并同帧多次测量漂移（WaterfallCore.tsx:488-494），并在卸载时 cancelAnimationFrame。
最新闭包正确长生命周期回调统一读 calculateLayoutRef，避免首帧闭包把列数改回旧值（:466-470）；core-props.test.tsx:144 有回归覆盖。
等值守卫正确syncFromCore 对 layout / viewport 做字段比较（withPlugins.tsx:312-330），值没变不触发 HOC 重渲染，避免布局完成后的空转。
插件隔离正确plugin-core 对 transformProps / transformData 逐插件 try/catch，且以插件对象引用为注册身份（plugin-core/src/react/usePluginRuntime.ts:96-117, :161-202）。
key 与定位正确key 走 keyExtractor；位置只写 transform / left-top，不移动 DOM 节点，滚动时不会重建整棵子树。
对象稳定化正确virtualize 用 JSON key 归一（:303-307），避免内联 virtualize 对象让 visibleRange 每次渲染都重算。

缺口

重渲染滚动时 Core 与 HOC 各一次 setState（P1-3 / P2-11），且 HOC 每次都重跑整条 transformProps 链，transformProps 结果没有 memo。
渲染期副作用ctxRef.current / transformedPropsRef.current 在渲染函数体赋值（withPlugins.tsx:220-221 / :357-358），并发渲染下可能提前可见。
effect 依赖layoutHooks 只依赖 namesKey（:303）；onPropsChange 依赖整个 props 对象（:348-354），父组件每次重渲染都会触发整条 props 钩子链。
热路径分配extendContext 每次布局/滚动都重建 context，并执行 computeVisibleIndexRange（O(n)）一次，getter 再随时重算（:158 / :193-200）。
列表渲染窗口内每项每次渲染都调用 renderItem，无 memo；非虚拟化 1000 项时每个滚动事件都全量 reconcile（P2-11）。
内存itemRefCallbacksRef 只增不删（WaterfallCore.tsx:743-753）；分析插件按 index 累计且不复位（P2-8）。
