01

核心数据流与职责边界

SKU 领域把「选择态」放进内核 state，把「禁用集 / 命中变体」作为渲染期派生值由 HOC 注入 context。 这条链路的风险点很集中：selection 是唯一可变输入，派生值每次渲染重算——入口一旦脏，整块矩阵就跟着脏。

① 规格数据

宿主传入 attributes（属性 / optionId）与 variants（attrValues / price / stock / quota）。

② 派生计算

extendContext 调 buildAvailability（禁用集）与 matchVariant（命中变体）。

③ Core 渲染

按 disabledMap 置灰按钮，读 selection 画选中态，摘要拼接 variant。

④ 写回 state

selectOption 覆盖/删除属性键 → base.setState({ selection })。

⑤ 事件扩散

onSkuChange + sku:change + onChange + onValidSkuChange；持久化 / URL / 埋点各插件订阅。

02

已验证成立的核心机制

这些最容易被误判成 bug，逐条对照代码与单测后确认成立，不作为问题上报。

✓禁用推导的「临时代入」语义正确

tentative = { ...selection, [attr.name]: option.id }，再用 keys.every 查是否存在任意变体匹配；只替换当前属性、保留其余已选约束，正是「选它之后还有没有活路」的定义。4 个纯函数用例覆盖。

✓缺货变体的 ignoreOutOfStock 语义成立

effectiveVariants 在默认 true 时过滤 stock === 0，只有缺货变体的选项会被置灰；显式传 false 时缺货变体参与推导。两个方向都有单测断言。

✓未选全 / 组合不存在都返回 null

matchVariant 先逐属性检查 selection[attr.name]，缺一即 null，再用 keys.every 精确匹配；blue+l 这类不存在的组合返回 null，摘要显示「无可售组合」。

✓再点同值取消 + 整段清空

selectOption 在 selection[attrName] === optionId 时删除该键，否则覆盖；clearSelection 直接写 {}。单测「再点一次同值 = 取消」与 ResetBar 用例均通过。

✓单选约束天然成立

SkuSelection 以属性名为键（一个属性只能存一个 optionId），没有数组/多值路径，因此单选是数据结构保证的，不依赖 UI 互斥逻辑。

✓首帧不触发 onChange

prevSelRef 初值 null，effect 里 if (prev === null || prev === selection) return；挂载时不会回调宿主，避免把「初始化」当成用户操作。

✓禁用态可读性已按对比度修正

禁用态不再叠 opacity，改为 #f2f3f5 底 + #6f757b 字 + not-allowed（SkuSelectorCore.tsx:127-129），避免白卡上「灰到看不见」。

✓插槽渲染异常被逐插件隔离

内核 renderPluginSlot 对每个插件单独 try/catch 并包 PluginErrorBoundary；一个价格插件抛错只丢自己那一段，核心规格按钮仍在。

03

P0 问题（阻断 / 超卖 / 白屏）

三条都落在核心链路上：选不了（矩阵死锁）、买多了（数量错误）、看不见（渲染崩溃）。 每条都给出触发路径与可直接落测的建议，不含推断。

P0-1 · 非法 / 陈旧 selection 会让全部规格按钮同时置灰，且无法点回来自救

P0
证据 1
packages/vane-sku/src/components/SkuPlugin/matrix.ts:63-69——只要 selection 里有一个属性值不在任何变体的 attrValues 中，该行所有候选的 tentative 都匹配不到
const tentative = { ...selection, [attr.name]: option.id };
const keys = Object.keys(tentative);
const exists =
  keys.length > 0 &&
  pool.some((v) => keys.every((k) => v.attrValues[k] === tentative[k]));
if (!exists) disabled.add(option.id);   // 其余属性的脏值把整行拖死
证据 2
withPlugins.tsx:82 用 defaultSelection 作为初值；UrlSyncPlugin/create.tsx:59-62 与 StatePersistencePlugin/create.tsx:45-53 把 URL / localStorage 里的任意键值直接 setState({ selection })，不校验属性名与 optionId 是否存在。
// UrlSyncPlugin :33-35
for (const [k, v] of q.entries()) {
  if (k.startsWith(prefix)) sel[k.slice(prefix.length)] = v;   // 值原样写入
}
// StatePersistencePlugin :51-53
const parsed = JSON.parse(raw) as SkuSelection;
if (parsed && typeof parsed === "object" && Object.keys(parsed).length) {
  context.setState({ selection: parsed });                     // 同样不校验
}
证据 3
SkuSelectorCore.tsx:107-118 用 disabled 真正禁用按钮，而「再点同值取消」的通道（withPlugins.tsx:60-67）挂在 onClick 上——按钮一灰，取消路径同时失效。
后果
换商品后残留的 localStorage（StatePersistencePlugin:35 固定单 key）、旧分享链接里的 ?sku_颜色=xxx、或后台改版把 optionId 换掉——任一场景都会让所有属性的所有选项同时置灰；因为无法点击，用户无法把脏值改掉，页面只剩「请选择规格/已选 颜色:xxx（回落显示原始 id）」。只有宿主额外装了 ResetBar 或拿 ref 才能恢复，属于核心功能死锁。
建议
在写 selection 的唯一入口做归一化：按 attributes 的 optionId 白名单 + variants 的 attrValues 过滤掉非法键值（UrlSync / StatePersistence / defaultSelection 三处复用同一个 normalizeSelection）；同时让已选中的按钮即使在 disabledMap 里也可点击「取消」。补单测：非法 defaultSelection 下至少保留可点的取消路径。

P0-2 · quantity 只做「展示层 clamp」，state 里的数量可以超过库存 / 限购

P0
证据 1
packages/vane-sku/src/custom-plugins/QuantityPlugin/create.tsx:47-50——上限只用来算 current（渲染值），不写回 state；onMount（:32-35）之后再没有写入点，插件也没有 onSkuChange 钩子。
const current =
  typeof context.state?.quantity === "number"
    ? Math.min(context.state.quantity as number, upper)   // 只影响显示
    : Math.min(defaultValue, upper);
证据 2
QuantityPlugin/create.tsx:52-56 只有用户点 +/− 时才写回 clamp 后的值；:9 注释与 doc.json 都声明「数量写进内核 state（key: quantity），宿主加购按钮直接读」。
后果
用户在库存 10 的规格上选到 5 件，再切到库存 2 的规格：UI 显示 2、加号禁用（看起来已经收敛），但 state.quantity 仍是 5；宿主按文档读 state 直接加购 5 件 —— 库存 2、限购 2 都会被突破，是最典型的超卖/金额错算路径。切回无变体（renderHeader :39 返回 null）时 state 也不会被清理。
建议
把「数量上限」收敛为单一事实：新增 onSkuChange（或 onValidityChange）在变体/库存变化时写回 Math.min(state.quantity, upper)，并在变体为空时清成 1；或改为「受控数量 + 提交前校验」。补单测：库存从 10 切到 2 后 state.quantity === 2。

P0-3 · attributes / variants 形状缺失直接在渲染期抛 TypeError，无错误边界 → 白屏

P0
证据 1
packages/vane-sku/src/components/SkuPlugin/matrix.ts:61,67 假设 attr.options 与 v.attrValues 一定存在；SkuSelectorCore.tsx:107 直接 attr.options.map。
for (const option of attr.options) {                    // options 缺失 → TypeError
  const tentative = { ...selection, [attr.name]: option.id };
  const keys = Object.keys(tentative);
  const exists = keys.length > 0 &&
    pool.some((v) => keys.every((k) => v.attrValues[k] === tentative[k]));  // attrValues 缺失 → TypeError
}
证据 2
withPlugins.tsx:40-41 的 ?? [] 只兜住顶层 null / undefined，不兜数组元素的内部字段；packages/plugin-core/src/react/slots.tsx:44-50 的 PluginErrorBoundary 只包插件插槽，HOC 与 Core 都没有边界，而异常发生在 extendContext（withPlugins:46-75），早于任何插槽。
后果
接口少下发一个 options（属性被后台停用后只留 name）、或某条变体漏了 attrValues，渲染期 TypeError 直接抛到 React 根节点，宿主整页白屏；插件隔离完全帮不上，因为它不在插件渲染路径上。空数组本身是安全的（buildAvailability 会把所有选项置灰），危险的是元素内部字段 undefined。
建议
加一层 normalizeSkuData(attributes, variants)：options ?? []、attrValues ?? {}、过滤重复 name/sku；HOC 外层再包一个 PluginErrorBoundary 提供降级 UI。补单测：{ name: "颜色" } 与 { sku: "x" } 不抛异常。
04

P1 问题（真实接入必然踩到）

这 3 条不会让页面白屏，但会让业务判定与展示分叉：缺货组合被当成「有效 SKU」、父组件无法控制选择、限购上限没有扣已购。

P1-1 · matchVariant 完全不看 stock，onValidSkuChange 对缺货变体照样触发

P1
证据 1
packages/vane-sku/src/components/SkuPlugin/matrix.ts:80-94——variants.find 只看属性值相等，没有 stock 条件；只有 buildAvailability 内部通过 effectiveVariants（:33-40）过滤了缺货变体。
const keys = Object.keys(selection);
return (
  variants.find((v) => keys.every((k) => v.attrValues[k] === selection[k])) ??
  null
);   // stock === 0 仍会返回
证据 2
withPlugins.tsx:126 if (variant) props.onValidSkuChange?.(variant) 只判非空；SkuSelectorCore.tsx:156-160 摘要也会渲染 ¥price · 库存 0。
后果
异步库存到达是常态（先返回商品基础信息、再轮询库存）：用户先选好组合，库存随后变成 0 时，variant 仍是命中对象，onValidSkuChange 仍把「有效 SKU」抛给宿主；叠加 ignoreOutOfStock=true 时按钮已灰，但摘要与回调仍宣告「可买」，宿主据此展示加购按钮。StockStatus 能显示「暂时缺货」，却无法阻止宿主加购。
建议
把「可售」定义收敛到一处：isPurchasable(variant, { ignoreOutOfStock })，onValidSkuChange 只在可售时触发；或给 matchVariant 增加可选参数复用 effectiveVariants。补单测：stock: 0 的命中变体不触发 onValidSkuChange。

P1-2 · 没有受控 selection：异步 / 父级重置写不回组件

P1
证据 1
packages/vane-sku/src/components/SkuPlugin/plugins/types.ts:75-110 的 props 只有 defaultSelection（:82-83）与 onChange（:90），没有 value / selection 受控入口。
证据 2
withPlugins.tsx:81-82 注释明确「选择态初值只生效一次（useState 语义）」；:119-128 的 effect 只向外发事件（onSkuChange / bus / onChange / onValidSkuChange），从不把 props 写回 state。
initialState: { selection: props.defaultSelection ?? {} },   // 只喂给 useState 一次
// 之后：props 变化 → 仅触发 onPropsChange 钩子，selection 不变
后果
服务端预选（defaultSelection 随订单/活动接口到达）、切换商品复用同一个组件实例、关闭弹窗后宿主想重置、或「选配套餐」按钮由父组件写入规格——全部无效；只能靠 key 强制重挂载或 ref 之外的黑招。异步数据先空后有也是同一问题：attributes 到达前 selection 为空，到达后无法由父指定。
建议
增加受控模式：selection?: SkuSelection + onSelectionChange（受控时 state 以 props 为准，effect 同步写回）；或至少让 defaultSelection 的引用变化触发一次 setState。补单测：更新 defaultSelection 后选中态与摘要同步变化。

P1-3 · 限购只判「是否超限」，数量上限没有扣掉已购件数

P1
证据 1
packages/vane-sku/src/custom-plugins/QuantityPlugin/create.tsx:43-44——byQuota 直接取 v.quota（每人总限购件数），不是「剩余可购」。
const byStock = typeof v.stock === "number" ? v.stock : Infinity;
const byQuota = typeof v.quota === "number" ? v.quota : Infinity;
const upper = Math.min(byStock, byQuota, config.max ?? Infinity);   // 未减 purchasedCount
证据 2
packages/vane-sku/src/custom-plugins/QuotaPlugin/create.tsx:29-33 只产出布尔 canPurchase = purchased < quota，不产出剩余件数；:68-69 的提示条也只展示「已购 N」。
后果
限购 2 件、已购 1 件时，canPurchase=true、数量上限仍是 2 → 用户可以再加 2 件，合计 3 件；宿主若只按 canPurchase 门控，会直接放行。这是购买规则被绕过，属于金额/数量口径问题。
建议
Quota 暴露 remaining = Math.max(0, quota - purchased)，Quantity 的 upper 取 min(stock, remaining, max)；canPurchase 由 remaining > 0 派生，两处共用同一函数。补单测：purchased=1 / quota=2 时 data-max=1。
05

P2 问题（可排期，不影响主链路）

契约、成本与可维护性问题；组合起来会显著拉高接入与排障成本。

P2-1 · 已选中的缺货 / 不可达组合无法主动取消（禁用按钮挡住 toggle-off）

P2
证据
SkuSelectorCore.tsx:117-118 disabled={disabled} 时 onClick 不会触发；而「再点同值 = 取消」的实现就在这个 onClick 里（withPlugins.tsx:60-67）。
后果
选项一旦被禁用推导置灰（例如库存变为 0），用户无法通过再点一次把它取消，只能整体 ResetBar（若未安装则完全卡住）；P0-1 的脏值场景正是被这一点放大成死锁。
建议
已选中的选项始终可点（禁用的只是「未选中且不可达」的候选）；或在按钮上提供显式移除。

P2-2 · 价格区间把缺货变体算进去，且价格 / 区间都不做格式化

P2
证据
packages/vane-sku/src/custom-plugins/PriceRangePlugin/create.tsx:36-44 只按已选属性过滤，不排除 stock === 0；:56-59 直接拼 min / max。PriceLink（PriceLinkPlugin/create.tsx:49-52）与摘要（SkuSelectorCore.tsx:159）同样直接插值。
后果
展示「¥199 – ¥229」时可能只有 199 有货，区间是虚假的；10.5 显示为「¥10.5」而非两位小数，NaN 会直接渲染成「NaN」。
建议
价格区间复用 effectiveVariants（与禁用推导同一口径）；抽出 formatPrice 固定两位小数并对非有限值兜底。

P2-3 · 重复 attr.name / option.id 无任何校验，会串选中态与 React key

P2
证据
SkuSelectorCore.tsx:100,112 用 key={attr.name} 与 key={opt.id}；matrix.ts:55-73 的 disabledMap 以属性名为键，重复 name 会互相覆盖。
后果
后台配置出现两个「颜色」或同一属性下重复 id 时，React 报 duplicate key 并可能丢行；selection 以 name 为键会同时点亮两个同名属性，看起来像「多选」——这正是单选约束在数据层被打破的形态。
建议
在归一化层校验 name / option.id 唯一性（开发环境 warn + 生产去重）；key 加索引前缀作为兜底。

P2-4 · 每次渲染全量 O(A·O·V) 重算，插槽与 context 全量重建

P2
证据
withPlugins.tsx:46-75 的 extendContext 依赖 [props, attributes, variants]；:40-41 的 ?? [] 在入参缺省时每次渲染都新建数组，依赖必然变化；:131-146 的四个插槽每次渲染重新调用 renderPluginSlot；usePluginRuntime.ts:138-157 的 context useMemo 依赖 extendContext。
const extendContext = useCallback((base: any): any => {
  const { disabledMap } = buildAvailability(attributes, variants, selection, {...}); // O(A·O·V)
  ...
}, [props, attributes, variants]);
后果
父组件任何一次重渲染（哪怕数据完全没变）都会重跑整张矩阵、重建 context 并让 12 个插件渲染钩子重算；SKU 面板常挂在商品详情页（轮询库存、倒计时、购物车角标都在触发父渲染），成本被持续放大。
建议
用 useMemo 以 [attributes, variants, selection, ignoreOutOfStock] 缓存 buildAvailability / matchVariant；插槽结果同样 memo；?? [] 提到模块级常量（rerender-memo / rerender-dependencies / js-index-maps）。

P2-5 · UrlSync 不校验键值、无 popstate；StatePersistence 单 key 不按商品分区

P2
证据
UrlSyncPlugin/create.tsx:29-37,59-62 原样读取任意 sku_* 参数并写 state，且只监听写入、未监听 popstate（前进后退后 UI 不还原）；StatePersistencePlugin/create.tsx:35,45-57 默认单键 "vane-sku:selection"，不区分商品/SKU 面板。
后果
多商品页或换商品后，A 商品的选中态会被还原到 B 商品（直接触发 P0-1 的全灰死锁）；同一页两个 SKU 面板共享一个存储键会互相覆盖；用户后退时 URL 变了但组件没变，分享链接与屏幕内容不一致。
建议
存储键加入商品/场景维度（key 必填或自动拼 skuId），读取时走 normalizeSelection；UrlSync 增加 popstate 监听并复用同一校验。

P2-6 · 插件实例重建后 onMount 不再执行（KeyboardNav 监听直接丢失）

P2
证据
withPlugins.tsx:98-101——onMount 只随 execute 跑一次（空依赖 + eslint-disable）；usePluginRuntime.ts:110-117 在插件数组变化时先 manager.clear()（执行旧 cleanup）再 registerAll；KeyboardNavPlugin/create.tsx:32-39,82-84 的 keydown 监听只在 onMount 里挂。
后果
宿主为下发新配置（限购数、埋点开关、价格策略）而重建插件数组时，旧监听被移除、新实例的 onMount 不执行 → 键盘漫游在运行中静默失效；UrlSync / StatePersistence 的初始还原也只会发生在首次挂载。
建议
插件引用变化时对新注册实例补跑一次 onMount（按引用 diff 只跑新增/替换项），或给内核加 onRegister。补单测：换插件数组后 keydown 仍生效。

P2-7 · 键盘漫游「方向键即选中」，且缺 roving tabindex / 组语义

P2
证据
KeyboardNavPlugin/create.tsx:62-68,77-80 找到下一个按钮后直接 next.focus(); next.click()——移动焦点等于改变选择；:36-39 过滤掉 disabled 后按实际下标取列，列位置会漂移。SkuSelectorCore.tsx:111-118 只有 aria-pressed，无 role="radiogroup" / aria-label。
后果
屏幕阅读器用户与键盘用户无法「只浏览不选择」；方向键每次移动都会触发 onChange、埋点、持久化与价格请求，误操作成本高；跨属性下移时列位置按过滤后的列表 clamp，落点不可预期。
建议
改为 roving tabindex：方向键只移动焦点，Enter/Space 才 click()；属性行加 role="radiogroup" aria-label={attr.name}，选项用 role="radio" aria-checked。

P2-8 · useImperativeHandle 依赖缺失、onPropsChange 引用比较、labelOf 渲染期重建

P2
证据
SkuSelectorCore.tsx:49-62 useImperativeHandle 依赖只有 [selection, variant]，containerRef 未列入（eslint 已报 warning）；withPlugins.tsx:107-113 用 prev !== props 判断，父组件内联 props 时每次渲染都触发 onPropsChange；SkuSelectorCore.tsx:72-73 labelOf 在渲染体内定义并每次 find。
后果
外部容器 ref 切换时 getContainer() 可能仍指向旧节点（KeyboardNav 依赖它取根节点）；每次父渲染都跑一遍 12 个插件的 onPropsChange 钩子链；选项多时摘要拼接产生 O(属性×选项) 的重复查找。
建议
补齐 containerRef 依赖；HOC 对 props 做浅比较后再触发 onPropsChange；把 labelOf 提到模块级或预建 Map<attrName, Map<optionId, label>>。
06

安全审查（security-best-practices）

结论：没有可利用的注入面。规格文案、价格、SKU 编码全部走 JSX 文本，未发现 innerHTML / dangerouslySetInnerHTML / eval / new Function（全包 grep 0 命中）。风险集中在「外部输入被当成可信选择」与「图片 URL 不受控」，均为低危。

注入与外部输入

XSS安全attr.name / opt.label / sku / label 全部由 JSX 转义；无危险 DOM 写入。
URL 参数低危UrlSyncPlugin 把查询串原样变成 selection（:33-35）。不构成注入，但会把任意字符串带进渲染与后续请求，是 P0-1 的直接放大器——应视为不可信输入做白名单。
本地存储低危StatePersistencePlugin 对 JSON.parse 结果只做 typeof === "object" 检查（:51-52），键值不校验；同源脚本可写 localStorage，同样属于不可信输入。
图片低危<img src={opt.image}>（SkuSelectorCore:134-140）接受任意 URL：外链追踪像素、http 混合内容、超长 URL 均不受限；无 XSS（img 不解析 HTML）。
埋点低危AnalyticsPlugin 上报完整 selection / variant（含 sku、price、stock，:39-46）。无用户身份字段，但属业务敏感数据，脱敏/采样由宿主负责。

凭证与运行边界

凭证未发现包内无 token / key / cookie 读写；发布仅 dist，demo 与测试不进包。
存储降级正确safeStorage 用 try/catch 包住 localStorage/sessionStorage 访问（:22-30），隐私模式静默降级；读写也各自 try/catch。
SSR守卫存在UrlSync / StatePersistence 均检查 typeof window === "undefined"；无顶层 window 访问。
请求宿主职责组件自身不发网络请求；加购、库存轮询、鉴权与 CSRF 不在包内边界。
建议对 opt.image 加协议/域名白名单；selection 归一化层同时充当安全边界（P0-1 / P2-5）。

React / 性能审查（vercel-react-best-practices）

按「状态单一来源 / 派生值缓存 / effect 生命周期正确」三条主线核对。主要失分项是 rerender-memo、rerender-dependencies、advanced-init-once。

成立的部分

状态单一来源正确selection 只在 base.setState 里写，插件不持有副本；禁用集与命中变体都是渲染期派生，没有双向同步。
事件后置正确onSkuChange 在 effect 里触发，不在渲染期 setState；首次挂载用 prevSelRef = null 明确跳过。
渲染纯净正确所有 renderHeader / renderOverlay 只读 context；Quota / Analytics 的写 state 都在生命周期钩子。
清理注册正确KeyboardNav 的 onMount 返回 cleanup 函数（:84），内核 clear() 逆序执行，卸载时监听不泄漏。

缺口

依赖失稳extendContext 依赖整个 props（withPlugins:74），父组件内联时每次渲染换引用 → context 与四个插槽全部重算（P2-4）。
派生未缓存buildAvailability / matchVariant 每次渲染全量 O(A·O·V)，没有 useMemo，也没有按 attrName/optionId 建 Map（js-index-maps）。
事件钩子过频onPropsChange 以引用比较（withPlugins:107-113），父渲染即触发整条插件钩子链（P2-8）。
ref 依赖useImperativeHandle 缺 containerRef（SkuSelectorCore:61，lint warning）；onMount 空依赖 + eslint-disable（withPlugins:98-101）。
